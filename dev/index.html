Being rebuilt

This package is being rebuilt to a new design, adopted on 2026-09-17: docs/ARCHITECTURE.md in the repository is what it is being built to, and IMPLEMENTATION.md is the order of the work. The round machinery described in earlier versions of this page is gone, and the pages below describe what is in the tree today, which is less than the site once documented and less than the design asks for.

What it is

GBGCodingTools.jl is a private Julia package, on GitHub, holding the review procedures, scans, test engines and writing rules of four Julia research packages: GBGPeriodicFields, GBGHomogeneousTurbulence, GBGStreamingStatistics and GBGCloudPhysics. AI coding sessions do much of the writing, testing and reviewing in those four packages; this package holds the rules those sessions are given and the scans, checks and test engines that verify the rules, so the four packages are held to one standard by the same programs.

Each of the four packages keeps only its own data, under its .gbg/ directory: its configuration, the disciplines its readers need, what it switches off and why, and its past reviews. It names one exact released version of GBGCodingTools, and nothing else passes between the package and this one. This package carries a .gbg/ directory too and is checked by its own tools.

The review procedures

The procedures, called instruments, are slash commands inside Claude Code (the AI coding tool the sessions run in); a person types the command, nothing starts them automatically. They are being rebuilt: the machinery that ran them — the rounds, their fix passes, their verifiers and the gate that froze a build while one was open — was deleted on 2026-09-17, and what replaces it is described in docs/ARCHITECTURE.md §3 and §4. Nothing a package's docs build or test suite runs reads review state any more.

The command-line program gbg

The program gbg is run from a terminal, in the directory of one of the packages. It is invoked as gbg <noun> <verb>, where the noun names what is acted on and the verb what is done, as in gbg sync --check; a bare verb is allowed where the noun is obvious, as in gbg check. There are 13 verbs, listed on The verbs, and every one exits with 0 when clean, 1 when it found something, 2 when it could not evaluate, 3 when it crashed. The two a person runs most:

  • gbg check — runs the rulebook over this package and reports what it finds. It repairs nothing: what a rule found is the work of whoever ran it.
  • gbg sync — writes every file that connects this package to that one, and with --check reports which of them has been hand-edited instead of writing.

What a package's docs build and tests call

  • GBGCodingTools.makedocs — what a package's docs/make.jl calls instead of Documenter.makedocs. It runs the documentation rules of the rulebook and the wiring check before building the site, and the rules that read the built site after.
  • GBGCodingTools.TestHarness — the engines a package's test/runtests.jl calls: a bound on what a call allocates (@alloc_below); recorded baselines for an in-place operation's reads and writes and for the public method set, failing the test suite when either moves unannounced; an oracle class on every public value-returning operation — analytic, independent, property, relational or structural, and none resting on relational alone; and a run of the witnesses kept from bug hunts.

The written rules

The policy is 92 rules, on The rules, each with an id like RULE.DOC.ARGCOV (every argument of a function appears in its docstring): a documentation rubric, the LaTeX idiom, the citation style, the testing protocol, the rules of the instruments, and git conventions. Each is a Julia value carrying its own check and the examples that show the check matches it; Render.policy writes them into every package, where the sessions read them.

How a package adopts it

Running gbg init in the package writes its .gbg/config.jl and then everything that config generates: the rulebook under .gbg/policy/, a managed block of the package's CLAUDE.md, the end-of-turn hook, and GBGCodingTools = "=X.Y.Z" in the docs and test environments. A small launcher script, also named gbg and installed once per machine by gbg install, runs whichever version the package in the current directory pins.

The module

GBGCodingTools — Module
GBGCodingTools

The one shared tooling package of the GBG Julia packages: the rulebook and the programs that check it, the docs-build wrapper, the test harness, the documentation review and the generated files that connect a package to all of that, at one version pinned by every consumer.

A consumer is a package that uses the tool — one of the four sibling GBG packages, or the tool itself. Each consumer pins the tool to one exact version, named in its .gbg/config.jl (tool: a released version, or :dev for a checkout), which gbg sync renders into the consumer's sub-environment compat entries. A consumer holds data; the tool holds behaviour; the only thing connecting them is that pin.

The module is a map; every part is documented at its home. The tree, each module naming only those above it, begins with the data:

  • Model — the types: a rule, a config, a finding, a run, a question, and nothing that acts.
  • Texts — reading the texts a rule is about, and finding a place in them again.
  • Catalogue — what this package knows, as values: the rulebook, the table, the disciplines.
  • ConfigIO — .gbg/config.jl, read as data and never evaluated.

Above them, what acts:

  • Engine — Checks runs a rule, Guard classifies a change, Questions asks the owner, Harness is what a package's test/runtests.jl calls.
  • Render — every generated file, and the wiring check that compares them.
  • Study — the rule wording study: agreement between readers, measured.
  • Orchestration — a run, its site, its scope and its agents; what no build or test may reach.

The command line is gbg <noun> <verb>: main dispatches the closed table VERBS, and the exit contract is 0 clean, 1 substantive finding, 2 cannot evaluate, 3 crash.

The verbs live under src/CLI/, one file per noun, each verb a function returning its exit code: Wire (init, sync), Check, Docfix, Answer, Run, StudyCmd, Bump, Release, Fleet, Install, Self and Git, the git questions the verbs ask.

Two engines a consumer's own build and tests call: makedocs, the mandatory wrapper around Documenter.makedocs, which reads no review state and nothing can freeze; and TestHarness, with Witnesses, the Julia-side engines a consumer's test/ runs.
