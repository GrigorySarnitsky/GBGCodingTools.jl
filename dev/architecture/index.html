GBGCodingTools — architecture

Written by AI, not regularly reviewed

This page is written by AI and is not reviewed regularly by a human.

This document is the design record of GBGCodingTools.jl: the one shared tooling package that four private sibling Julia packages consume — GBGPeriodicFields (PF), GBGIsotropicTurbulence (IT), GBGStreamingStatistics (SS), GBGCloudPhysics (CP) — and which consumes itself: the tool repository is its own fifth consumer (D15). It is self-contained: every term is bound where it first appears, and no external file is needed to understand it. Evidence citations point into the design-time surveys (survey-*.md, round1-*.md, round2-*.md, facts-claude-code-platform.md, theory-patterns.md) by file and line; those files are the historical basis, not a dependency of the reader. 04-decision-record.md is the authoritative decision record; where this document extends it, §10 says so explicitly.

Vocabulary used throughout:

  • Consumer — one of the four packages, as a client of the tool; and the tool repository itself, its own fifth consumer (D15) — a statement about "a consumer" binds the tool root too unless it says otherwise.
  • Instrument — one of the four review procedures the tool ships: /check-docs (the deterministic
    • agent battery over documentation), /check-consistency (the multi-hat panel over the rendered
    site), /bug-hunt (the code instrument whose only evidence is a failing program), /audit-changes (the diff audit). "Instrument" keeps the house meaning of a measuring device.
  • Round — one run of an instrument, recorded as a tracked directory in the consumer.
  • Lane / hat — one agent of an instrument (a hat is a persona in the panel; a lane is a surface or territory in the other three). Agents run inside Claude Code Workflow scripts (sandboxed JavaScript with no filesystem, configured only through an args object).
  • Anchor — a hat or lane that runs at full strength instead of the economy model. This is the sense every unqualified use below carries; the word has two others that are always qualified — a file#heading anchor, the Markdown reference Config.resolve_anchor resolves, and a seed class's anchor, the regular expression marking where a seed is planted. Which engine lanes are anchors is a constant of the catalogue (the executing audit lane, the two free hunt lanes, the dismissal auditor, the severity re-check); which domain hats are anchors is the consumer's config (anchor = true|false per hat). The never-economised phases (D18) are a different thing and are never called anchors.
  • Gate — a program whose non-zero exit blocks a build, a test run or a round's closure.
  • Pin — the tool version a consumer names in its config.
  • Managed file — a file the tool renders into a consumer and hash-checks thereafter.
  • Ledger — the consumer's one file of declared exceptions (.gbg/exemptions.toml). The word is reserved for that file; the bug-hunt's per-finding fixed|refused|escalated record is the disposition record (reproductions/<id>.json), never "the ledger".
  • GBG_ROUND — the environment variable the CLI exports (GBG_ROUND=<round-id[,…]>) whenever it invokes make.jl, Pkg.test() or an executable claim on behalf of an open round; gbg gate ignores exactly the open rounds it names and no others (§6.2 step 10).

§0 The design sentence and the requirements

A consumer holds data; the tool holds behaviour; the only thing connecting them is a pin. Every engine, protocol, persona catalogue, verdict vocabulary, gate, lint, harness and policy text lives once, in the tool, at a version. A consumer carries one config file, one exemptions ledger, its domain hats, its tracked rounds, and a handful of hash-stamped stubs it regenerates rather than edits. What differs between consumers is either a value the config schema admits or an entry in the ledger with a reason — nothing else is admissible, and gbg doctor says so.

Requirements (the frame every decision in §2 answers):

IdRequirement
R1Uniformity. The four consumers run the SAME instrument code at the SAME version. A difference between consumers is either declared config or a doctor finding. Existing differences default to historic artefacts.
R2Transparency. From committed artefacts alone one can answer: which instrument version measured this round; what this package deviates in and why; what changed in the instrument between two rounds.
R3Fail-closed. The missing case is the failing case: no config → fail; absent round directory → fail; dead lane → cannot evaluate; zero count → dead agent, never clean.
R4Instrument integrity. Instrument changes are their own commits and releases, never folded into a round. A round records its instrument version and cannot close under a different version than it opened with unless re-graded.
R5Self-tested. The tool tests itself against a fixture consumer with must-fail arms; a check that cannot fail is not a check.
R6Minimal consumer footprint. A consumer holds config, piles, and the files that must physically exist (test/regressions/, the make.jl call, the CLAUDE.md import line); nothing else duplicated.
R7Polyglot reality. Workflow JS (no filesystem, args only), Julia, shell, markdown skills, personas, hooks — versioned together; every deterministic engine is Julia inside the one package.
R8Two-machine fleet (Aiporetne, Enteropia; Dropbox + private GitHub), reproducible per-machine install, no secrets in any repo.
R9Migration tractability. Each consumer migrates by an ordered checklist, a doctor check verifying each step; no big bang.
R10Extensibility. A fifth package = config + scaffold. A new instrument = one directory with a contract (skill, workflow, engine, self-test, schema).
R11Comparable measurements. One shared finding schema and verdict vocabulary; per-package extension only through declared fields.
R12Shared cost policy. Economy lanes by default, anchors named per package, fix phase at full strength.

§1 The platform / product model

The tool is a platform; each consumer is a product instantiated from it by configuration (theory-patterns.md:9-19). The commonality/variability analysis below is the deliverable that turns "1.5–2× line-count drift on same-named files" (survey-buildlints-hooks-policy.md:173) into a list.

Common (lives once, in the tool): every Workflow engine; every deterministic scan and gate; the Julia test harnesses and the docs-build wrapper; the verdict vocabularies and schemas; the demotion and closure predicates; the round layout and stamp fields; the exit contract; the generic hat and lane catalogues; the seed mechanism (a consumer's seed catalogue is the consumer's own .gbg/seeds.toml, §6.4; only the fixture's lives in the tool); the policy prose with its rule ids; the doctor; the fixture consumer and self-tests; the cost policy's never-economised phases and the economy model name; the rubric's constants (the upright $\mathrm{i}$, the $\partial_{x_i}$ partial, the "Allocating form of" and "The fields are" phrases, the ≥ 3-arguments-or-a-keyword threshold — none of them a config key).

§2 Decisions D1–D19

Each decision: choice / forced by (requirement + evidence) / dominated alternatives.

D1 — Unit of distribution: one repository, one version, two faces

Choice. One git repository GBGCodingTools.jl (private GitHub GrigorySarnitsky/GBGCodingTools.jl; dev checkout ~/Dropbox/Research and Teach/AI Helpers/GBGCodingTools/) that is simultaneously (i) a Julia package (root Project.toml, module GBGCodingTools) which carries the CLI gbg as src/CLI/*.jl, the scan engine as src/Scans/*.jl, the harness and the docs-build wrapper, and (ii) the instrument corpus (protocols, Workflow .js, catalogues, schemas, policy, templates, fixture). One version, one tag per release, one CHANGELOG.md. Every deterministic engine is Julia inside that one package; JavaScript exists only for the Workflow scripts, sh only for the shim and the Stop hook; there is no Python (the one transitional exception, D8's consolidate.py, was deleted on 2026-09-09 when its Julia port passed the byte comparison).

Forced by. R1, R4, R7, R2. The divergences that must be resolved rather than parameterised all cross a language boundary: verify-fixes.js (JS) and lint_review_closure (Julia) were declared twins and desynced for a day (survey-checkdocs.md:207, survey-buildlints-hooks-policy.md:229); the hunt verdict set is keyed off by dismissals.js, closure.py, finished.py (survey-bughunt-auditchanges.md:263). Splitting by language recreates those twins across repos — and a second implementation language inside the one repository recreates them inside it, which is why the first draft's Python CLI was retired for Julia (D8).

Dominated. Julia package + separate Claude plugin repo: two versions, and a plugin cannot ship Workflow scripts (facts-claude-code-platform.md:62). Vendored copies + manifest: the status quo (survey-checkdocs.md:167, MANIFEST listing 3 of 6). Monorepo of all five: a topology change to four working repos with their own docs deploys; not needed to get the one-version rule.

D2 — Delivery: Pkg fetches the pinned copy; a per-machine sh shim that execs the docs environment's copy; a registered dev checkout for the owner

Choice. Three roles, three locations:

  1. Dev checkout — the Dropbox clone above, pushed to GitHub. The owner edits and releases here. Consumers never read it. Its path is registered per machine in ~/.gbg/dev (one line, the absolute path), written by gbg install [--dev-checkout <path>] or by install.sh; nothing else lives under ~/.gbg/.
  2. Pinned copy — fetched by Julia Pkg into ~/.julia/packages/GBGCodingTools/<slug>/ from each consumer sub-environment's Project.toml [sources] entry (D3) at an immutable tag. Files are read-only by Pkg convention (round2-maintainer.md:10-17, E1) — and, because convention is not a check, gbg self verify re-hashes the tree (D3). Every consumer-side invocation — CLI, Workflow scripts, protocol text, Julia harness — runs from this copy.
  3. Shim — ~/.local/bin/gbg, POSIX sh, ~30 lines, versionless, and it selects no depot slug: walks up from $PWD to the nearest .gbg/config.toml (as before) and then exec julia --startup-file=no --project="<root>/docs" -e 'using GBGCodingTools; exit(GBGCodingTools.main(ARGS))' -- "$@". Pkg's resolution of the consumer's docs/ environment IS the version selection — stronger than a slug match, because the manifest and the [sources] entry decide. A docs/Manifest.toml that is absent or does not list GBGCodingTools is "package not instantiated" → exit 2 with the hint julia --project=docs -e 'using Pkg; Pkg.instantiate()'. Outside any consumer (no config found) it execs the same line against --project="<dev checkout>" read from ~/.gbg/dev, for fleet, release, new, selftest; no ~/.gbg/dev → exit 2 "no dev checkout registered". gbg --dev … (the shim's first argument; main accepts the same flag and sets GBG_DEV=1) inside a consumer routes to the registered dev checkout and stamps tool_version = "dev+<sha>[-dirty]"; a documentation round does not open at such a stamp (Preflight.dev_round), and one already closed at it is cited by no release (D16, revised 2026-09-10). A config whose pin is the literal version = "dev" is legal in exactly two places (D15): a consumer enclosed by the tool repository — the fixture — which is routed the same way, to the enclosing tool repository (found by walking up to a Project.toml with name = "GBGCodingTools", execed as its --project), else exit 2; and the tool's own root, where the walk stops at its first step because the root holding .gbg/config.toml IS the tool repository, so the shim takes its ordinary route — --project="<root>/docs", the tool's own docs environment. Bootstrap circularity, stated once. The tool's docs/Project.toml lists GBGCodingTools with [sources] GBGCodingTools = {path = ".."}, so that environment loads the tool from its own working tree; the shim, run inside the tool repository, execs julia --project=docs there like anywhere else, and every gbg call the tool makes on itself therefore runs the working tree — equivalent to --dev — the PIN.* checks accepting version = "dev" at the tool root and the stamp recorded as dev+<sha>[-dirty], or as the tag itself for a round opened while the tree is clean at a released tag (D16). The tool's docs environment is instantiated once per machine (julia --project=docs -e 'using Pkg; Pkg.instantiate()' in the dev checkout), exactly as a consumer's must be. The Julia start (~2–5 s including package load) is paid once per shim invocation; where that cost is accepted and where it is forbidden is stated in D6 and D13.

Bootstrap on a new machine: Pkg.instantiate() in any consumer's docs/ env (over the same https credentials the fleet already uses for private sibling deps), then, from that consumer, julia --startup-file=no --project=docs -e 'using GBGCodingTools; exit(GBGCodingTools.main(ARGS))' -- install --dev-checkout "<dev checkout>", which writes the shim and ~/.gbg/dev; the copy that runs is the one Pkg resolved, so no glob over depot slugs is ever expanded. install.sh in the dev checkout runs the same verb against the checkout itself — a convenience, not the contract. From inside the dev checkout the shim's walk finds the tool's own .gbg/config.toml (D15), so fleet, release, new and selftest run there through the tool's docs environment — the same working tree ~/.gbg/dev names; the registered path serves the calls made from outside any consumer.

Forced by. R8 (survives a fresh clone and CI without Dropbox or ~/.gbg), R6, R4 (the pinned copy is an immutable tree — a mid-round git pull of a live checkout would change gates under an open round, round2-measurement.md:57-73). The shim execs the docs/ environment and no other because Pkg.test() leaves no test/Manifest.toml (round2-maintainer.md:10-17), so a --project=test lookup is dead on the very machine that ran the tests, while docs/ always carries a manifest — the same fact that made the first draft's shim look in --project=docs territory for its slug match; a consumer whose docs environment is not instantiated is exit 2, never a silent fall-through to the dev checkout (round2-measurement.md:84-90, A8). The dev checkout must be registered rather than baked into the shim because install runs from the pinned copy, which cannot know where the owner's checkout is, and SHIM.HASH requires the installed body to equal bin/gbg byte for byte.

Dominated. One clone in Dropbox + ~/.gbg/tools symlink (round1-consumer): fails a fresh clone (nothing reports the missing policy), deadlocks a staged upgrade (one checkout at one tag fleet-wide while bump is refused under an open round), and a checkout on one host flips the other's within seconds (round2-maintainer.md:53-90, S1–S5). Per-machine clone + git worktree per tag (round1-measurement): three copies of one tag per machine, one of them writable, that a doctor must prove byte-equal — the twin class the tool exists to abolish (round2-maintainer.md:92-101). Plugin marketplace: no per-project pin, no auto-install on clone, no Workflow shipping (facts-claude-code-platform.md:114,121,370-372). Private Julia registry: strictly better once there are several releases; deferred, a pure upgrade of D3's pin syntax. Julia 1.12 workspaces: would collapse the sub-environment entries to one; deferred, untested in the fleet. A dev-checkout path substituted into the shim at install time: breaks SHIM.HASH, which is why the path is a separate one-line file. Selecting the depot slug whose Project.toml version equals the pin (the first draft): a weaker match than Pkg's own resolution — two slugs at one version are told apart only by the manifest, which that shim never read.

D3 — Binding: [sources] url + rev (https) rendered from one pin into every sub-environment that lists the tool, [compat] = "=x.y.z" as a second witness, the pinned tree re-hashed

Choice. .gbg/config.toml [tool] version = "1.0.0" is the source. gbg sync renders into every Project.toml under the consumer whose [deps] lists GBGCodingTools — test/, docs/ and benchmark/ by default, and any further sub-environment that lists it (PF's test/gpu/*, benchmark/gpu/*, examples/ if they ever do):

[deps]
GBGCodingTools = "<uuid>"
[sources]
GBGCodingTools = {url = "https://github.com/GrigorySarnitsky/GBGCodingTools.jl.git", rev = "v1.0.0"}
[compat]
GBGCodingTools = "=1.0.0"

The URL is https — CP's and IT's CI rewrite only https://github.com/ through url.<token>.insteadOf (round2-maintainer.md:24-26,70-72); an SSH form would break the existing auth. Tags are immutable: gbg release refuses to re-tag. PIN.TREESHA compares the git-tree-sha1 recorded across every sub-environment Manifest.toml that exists (docs/, benchmark/, and test/ when Pkg.instantiate() wrote one — Pkg.test() writes none) with the tree_hash that Pkg.dependencies()[uuid] reports for the copy the docs/ environment resolves: WARN for a sub-environment without a manifest, FAIL on disagreement. gbg self verify — run at the start of every gbg round verb and of gbg gate — recomputes the git tree hash of the copy it is running from (pkgdir(GBGCodingTools); blob and tree hashing in Julia on the SHA stdlib, src/TreeHash.jl, no git needed), compares it with Pkg.dependencies()[uuid].tree_hash and the manifests' git-tree-sha1, and asserts that entry's is_tracking_repo && !is_tracking_path — a Pkg.develop'd copy lives INSIDE the depot at ~/.julia/dev, so a path-prefix test cannot tell it from a fetched one: an edited or dev'd pinned copy is exit 2; no manifest to compare against is WARN; a dev pin skips it with WARN. ROUND.toml records the computed hash as tool_tree_sha. The tool is never a [deps] of the package proper (theory-patterns.md:148-149).

Forced by. R8, R1/R4 (immutable ref, theory-patterns.md:25-27), R2 (git log -p test/Project.toml answers when the pin moved). [sources] is honoured only when that project is the active environment — exactly the sub-environment cases (theory-patterns.md:144-146; Pkg.test() verified, round2-maintainer.md:10-17). A sub-environment left out of sync resolves the tool outside the pin, silently (attack 10.3), so the walk covers every one that lists it. Nothing but a re-hash can tell an edited read-only tree from the tag it claims (attack 4.1): tool_rev is read from a manifest an edit never touches.

Dominated. ~ symlink / env var / plugin root: machine state, invisible to git. [sources] path = ../../AI Helpers/…: binds to whatever is checked out, so the pin is not a pin, and breaks CI and clones outside Dropbox. Submodule: two-step clone, Dropbox does not carry .git state reliably (theory-patterns.md:33-35). Vendored copy: the disease. A TREE.sha256 shipped by release: a second artefact to keep honest, where the manifests already carry the hash Pkg computed.

D4 — Pinning: fleet-wide one version is the rule; the per-consumer pin is what makes it checkable; a dated window

Choice. All four pinned consumers pin the same MAJOR.MINOR.PATCH (the tool's own fleet row, D15, is the tree they pin and pins nothing). Detection: gbg doctor in a consumer (pin ≠ resolved version, entries disagree, tool dev'd in a manifest); gbg fleet from the dev checkout (reads fleet.toml, one row per consumer; a path that does not exist is exit 2, never a skipped row); a round's ROUND.toml names its version, so gbg fleet --diff (below) refuses unequal MAJOR.MINOR. An upgrade is a sweep: gbg bump in the canary (PF), its full gate, then the other three. Two distinct pins are tolerated for a 7-day window and fail afterwards; the window is checked by gbg fleet and by gbg bump, and it is gbg bump that starts it — a bump that would leave the fleet at two versions records the window start in fleet.toml [sweep] (started, from, to). preflight does not check the fleet: a consumer has no fleet.toml and no network is assumed. gbg bump refuses (exit 2) while a round is open unless --abandon-open-rounds "<account>". gbg fleet reports every pinned consumer at 1.0.x after migration; its fifth row, the tool's own, is the tree they pin (below).

The gbg fleet output contract. One row per fleet.toml consumer, <name> <pin> <status> <detail>, with status one of: OK — .gbg/config.toml present, its QUICK doctor set green (the whole table under --deep) and its pin equal to the fleet's newest pin; NOT-INITIALISED — the consumer path exists but holds no .gbg/config.toml (a consumer before gbg init; <pin> prints —); BEHIND — its pin is older than the newest pin in the fleet (detail names both pins and the window state: within window while [sweep].started is less than 7 days old, window closed after, no window when [sweep] is absent — the normal state of a converged fleet and of a fresh dev checkout); RED — its doctor fails (detail lists the failing ids). Exit 0 when every row is OK; 1 when any row is NOT-INITIALISED, RED, or BEHIND outside the window (BEHIND within the window is printed as a WARN row and keeps exit 0); 2 for a path that does not exist or a missing fleet.toml. The tool's own row. fleet.toml carries [[consumer]] name = "GBGCodingTools", path = "." (D15), so the fleet lists the tool as its fifth row: <pin> prints dev+<sha>[-dirty], <detail> says clean at vX.Y.Z or off tag, and status is OK or RED by its own doctor alone — the row is excluded from the newest-pin computation and BEHIND is never computed for it, since it is the tree the other rows pin rather than a copy of it. gbg fleet --diff <consumer>:<round> <consumer>:<round> prints two closed rounds' tallies side by side (the two may sit in one consumer) and refuses (exit 2) when their tool_versions differ in MAJOR.MINOR — the cross-version comparison R11 forbids. It is not gbg round compare, which has exactly one meaning: the Step-0 comparison of a re-graded imported round against a hand-transcribed record (§8).

Forced by. R1, R2, R4, R11 (comparable only at one version, theory-patterns.md:99-101), and R9: a sweep is sequential, and a PATCH released for a defect Phase 5.1 finds may land while PF is mid-round, so two versions must coexist briefly and visibly (round2-maintainer.md:74-82,117-123).

Dominated. Per-consumer pins, no fleet rule: R11 fails. Fleet version read from the dev checkout, no per-consumer pin: not checkable on a clone. preflight polling git ls-remote --tags: a network dependency inside a skill's ! block, and offline it degrades to a WARN nobody reads.

D5 — Config: one TOML file, one layer, one validator (Julia), Workflow args rendered by the CLI

Choice. .gbg/config.toml (not under .claude/, which is Claude Code's discovery namespace). Format TOML (the TOML stdlib). Schema schema/config.schema.json: closed keys (additionalProperties: false), explicit required, closed enums; unknown key, missing required key, unknown enum member, a path that does not exist → exit 2. No layering: no local file, no env overrides, no defaults hidden in code — gbg init materialises every default into the file; machine facts (hostname, GPU vendor, Threads.nthreads()) are read at run time and shown by gbg doctor --effective. One validator, in Julia: src/CLI/Schema.jl is the JSON-Schema-subset validator (types, required, enum, pattern, additionalProperties, nested objects and arrays) applied to the TOML.parsefile Dict — no JSONSchema.jl dependency, the subset being small and a dependency being a second implementation to trust. Config.read() is that validator called in-process, defaults materialised; gbg config --toml|--json print the same validated object for humans and scripts, and nothing else parses the config. Config reaches Workflow scripts only as the args object the CLI renders — by ONE renderer, Preflight.jl's, which gbg preflight and gbg round pass open both call. The FIVE rubric variation points are config enums (§1); everything else the rubric says is a platform constant or a ledger deviation. The one schema extension point is [schema] finding_types_extra.

Forced by. R3, R11, R2, R7 (facts-claude-code-platform.md:163-174: args only). Four copies of one surface list inside PF alone (survey-checkdocs.md:112); the layering trap (theory-patterns.md:129-131). Two validators is the twin class (round2-maintainer.md:173-182). A threshold or an idiom string in config is the R1 divergence channel with a schema around it (attack 9.1, 9.2): IT at 5 and PF at 3 under one rule id would be two rules.

Dominated. JSON: no comments, and the ledger carries prose reasons. YAML: no stdlib parser. Project.toml [gbg] table: Pkg rewrites the file; Aqua flags it. Layered defaults/local/env: archaeology. §6.2 /check-consistency end to end

  1. Skill. /check-consistency [--profile all|core|explicit] [--strength full] [--no-seed] [--dry]. The stub's ! block runs gbg preflight check-consistency $ARGUMENTS; --dry opens nothing and prints what would be run.
  2. Preflight (exit 2 aborts the skill): validates config; quick doctor (QUICK); the torn-file guard CFG.TORN — exit 2 when git status --porcelain shows any PINNED file (one the consumer owns and the tool never renders) or MANAGED file (one gbg sync renders and hash-checks) modified, round files under an open round excepted — which preflight and every gbg round verb run and which QUICK does not carry (a file that fails to parse is CFG.VALID); gbg self verify; refuses on an open check-consistency round, pin ≠ resolved, an uncommitted change under a closed or abandoned round; writes .gbg/rounds/<date>-check-consistency-<NN>/ROUND.toml (roster resolved from profile + config, a hat with an empty substrate recorded not_applicable rather than expected; stamps incl. config_sha and tool_tree_sha; opened from the CLI clock — a Workflow script cannot call Date.now()); prints the protocol text, the Workflow call (args: {round_dir, scratch_dir, manuscripts, hats[{key, persona, anchor, substrate, siteonly}], preamble, deliberate_absences, adjudicated_titles[], cost, strength, finding_types, finding_cap, opened}), and the next-step line. Hats receive the adjudicated list as titles only, never ids, never seeds. A hat reports CLASSES, never sites — a mistake recurring across pages is ONE finding whose locations name every page (RULE.DOC.CLASS_SWEEP), and candidates_found counts classes — with finding_cap bounding those findings. The cap is config, never a literal in panel.js: a cap is a policy number, and no package datum belongs in a Workflow script.
  3. Prepare. gbg round prepare <round> (the session runs it per the protocol): exports GBG_ROUND=<round> and runs docs_build, requiring exit 0 (a failed build is exit 2 with the log path) — the wrapper's gbg gate inside that build ignores exactly this round; consolidates docs/build into .gbg/scratch/<round>/manuscript-{full,siteonly}.md; if seeding, selects the seeds from the catalogue with a per-round salt (the round id salts the nth-occurrence offset of every class, so two rounds never plant the same set) and plants them into the manuscripts in place — during the panel ONLY the seeded manuscripts exist under .gbg/scratch/<round>/; ground_truth.json is NOT written yet.
  4. Panel. Workflow({scriptPath: "<root>/.gbg/scratch/<round>/workflow/panel.js", args}) — the copy preflight wrote from the pinned copy's instruments/check-consistency/workflow/ (D7, V1). Hats run in parallel; each is told to Write findings/NN-<key>.json FIRST, then return the same object (schema-forced); each is forbidden to open .gbg/** and ~/.gbg/** except the payload files its args name — its manuscript, its persona, the rulebook where its needs grant it (never a substrate value: the substrate enum is full | siteonly and narrows the CORPUS, nothing else) — under .gbg/scratch/<round>/workflow/payload/ (D7, Revision 9). The script returns {written, dead, empty, truncated} and logs the next line. No tally.
  5. Bank. gbg round bank <round> (like every gbg round verb it runs gbg self verify and CFG.TORN first): refuses a changed config_sha (exit 2 → pass open --regrade); validates each expected lane file against instruments/check-consistency/schema.json; records the sha of every present lane file at first sight in ROUND.toml.lane_shas; classifies (D10) — absent, unparsable or invalid ⇒ DEAD, the last two quarantining the file as NN-<lane>.rejected.json (there is nothing to quarantine when it is absent); assigns ids; regenerates the UNSEEDED manuscripts (a fresh consolidation), recomputes ground truth deterministically from the seed catalogue, the salt and the unseeded manuscript, and writes ground_truth.json; marks seeded findings by fragment match; prints recall per class (skipped classes UNDEFINED, kept in the denominator and named) and flags SUSPECT every hat with ≥ 2 seeds on its substrate and zero matches (reported in the tally, not fatal); writes findings.json and findings_sha; renders findings.md + SUMMARY.md (seeded hits subtracted, corroboration with a denominator, capped hats marked — a reading aid). Any DEAD or REJECTED lane ⇒ exit 2 and NOTHING is frozen (lane_shas stays). gbg round rerun <round> --lanes … accepts only lanes bank classified DEAD; a live lane whose sha changed since first sight is REJECTED.
  6. Fix pass — on the owner's word, at session strength, driven from findings.md by finding id, never from SUMMARY.md. A build or test run during the pass is gbg round build <round> / gbg round test <round>, which export GBG_ROUND around docs_build / julia_test; a bare julia --project=docs docs/make.jl under an open round is refused by the gate, by design.
  7. Verify. gbg round pass open <round> refuses a changed config_sha unless --regrade, and refuses outright — --sweep-ok overrides — while an open finding names a file the fix pass did not touch, since a pass spent learning that a fix stopped at the line it quoted is a pass wasted (the rc.1 round spent five of ten that way). It creates verdicts/pass-<k>/, records head, range (<opened head>..HEAD), the nonce, expected, the scope, the stamps; regenerates the manuscripts after a fresh build under GBG_ROUND; prints two Workflow lines rendered by Preflight.jl's renderer (the one renderer; pass open renders no args of its own): verify-act.js (sees the diff; args add range, pass_dir, nonce, expected) and verify-state.js (blind; no range; same nonce). Both forbid their agents to open .gbg/** and ~/.gbg/**; both require graded_sha256 and pass_nonce; both receive every finding's text unabridged, so a real defect co-quoted with a seed is graded on its own claim. Seeded findings are graded by the state verifier only. A pass after the first verifies only its scope: the ids the previous pass left open, any it closed whose named locations the fix pass has since touched, any it closed that names no location at all, and any it left pending_state — a closed finding being able to regress only where its own evidence lives, and one with no evidence anywhere being re-verified every pass rather than never. The act verifier grades the open ids; a closed id back in scope is a RE-CHECK, which the blind verifier alone reads: the question is whether it regressed, and its fix is not in this pass's diff, so the act verifier could only ever say UNDONE — 22 of 2026-09-10-check-docs-03's 40 ids closed by adjudication for that alone. Every other id keeps the entry that closed it. The rc.1 round verified 56 findings ten times over where 90 verifications were owed, and the panel is the round's whole cost. A round has a pass budget, max_passes (3 by default for both doc instruments): past it pass open refuses, and a --regrade whose fix range changed no covered file does not spend it.
  8. Grade. gbg round grade <round>: refuses a changed config_sha (exit 2); validates both verdict sets; a file whose graded_sha256 or pass_nonce mismatches is REJECTED, an absent one DEAD (exit 2); applies Demote.jl (HONORED → LINE-ONLY iff class_surfaces == [] or any entry is swept: false, counted apart as demoted_by_rule); keeps a re-checked id closed on the act verdict that closed it while the blind verifier still reads it ABSENT, and reopens it when not; applies the closure channels (§6.5); writes tally.json/tally.md; prints the pass series and the plateau signal; exit 1 while open_ids is non-empty and equally while any id is pending_state — closed by the act verifier with no blind reading to confirm it. Loop 6–8 over the same findings.json; it terminates because the set is finite and closure is per finding.
  9. Close. gbg round close <round>: requires the latest pass open_ids == [], no DEAD lane, every expected lane graded in that pass, config_sha and tool_version unchanged since open or the round re-graded (else a refusal line and exit 1 — close reports it as one condition among the rest, where every other round verb exits 2 → pass open --regrade), tool_tree_sha unchanged under the same tool_version (else "tag moved" → abandon-only), ROUND.toml.head an ancestor of HEAD (git merge-base --is-ancestor; else pass open --regrade), the round's existing files committed; runs dismissals.js over every scope = "finding" ledger entry recorded after opened and requires reopened == [] — for EVERY instrument, not the hunt alone; snapshots the adjudicated ids used into ROUND.toml.closed_by; writes closed, closed_head, the tally sha (its own writes are what the session then commits and pushes). gbg round abandon <round> --reason "…" writes abandoned = {reason, open_ids} and carries the round's deferrals into the work queue as close does — a plateau is the usual reason, and it is a decision the diff shows. Once the pass budget is spent, close carries every id still open or never blind-read into the next round of the instrument, on a blind severity re-check, a blocker or major among them: the budget and not the severity stopped the loop, so severity decides releasability instead, and a final release refuses while a carried serious finding stands.
  10. Gate. gbg gate [instrument…] — the CLI face of gate(instruments...), called in-process as gate("check-docs", "check-consistency") by GBGCodingTools.makedocs and as gate("bug-hunt", "audit-changes") by TestHarness.gate(), bare (all four) as gbg gate by hand and by the CI snippets: it runs gbg self verify first; scans every round directory, enabled instrument or not; any open round → 1 (names it) — EXCEPT the rounds named in GBG_ROUND, which the CLI exports only while it invokes a build, a test or an executable claim on behalf of that open round (prepare, build, test, pass open, close, audit-changes bank); an open round of a disabled instrument → CFG.VALID FAIL; in a working tree (not CI) an open round whose directory is untracked or modified while HEAD ≠ ROUND.toml.head → 1 (the fixes were committed without the round); a round directory without ROUND.toml → 2; .gbg/rounds/ absent while instruments are enabled → 2 (ROUND.DIR: the gate fails, never passes vacuously, when the round directory an enabled instrument implies is absent — the closing of the vacuous-pass hole both freeze notes recorded); closed rounds are NOT re-graded on every build (their tally is frozen with its hash); re-grading is explicit (gbg round pass open --regrade). CI never sets GBG_ROUND, so the commit/CI gate stays fail-closed; a GBG_ROUND set by hand outside a CLI invocation is a stated residue (§11). The Stop hook of D13 runs in every consumer, and its body is the managed sh file — PF's queue-guard.sh verbatim, which guards WORK_QUEUE.md and never reads a round — never a Julia call; it is not part of the gate.

The pass budget. A hunt has max_passes passes (3 by default), as the two doc instruments do; past it close carries every finding still open, which then owes the round no disposition and is left out of the arithmetic. A carried hunt finding takes its evidence: its carry entry records its kind, the verdict it was confirmed with and its witness (Passes.hunt_carry_fields), and the next hunt's bank copies that witness in under a name of its own and re-runs it (Rounds.rebank_hunt_carried!).   • The fleet window is checked only where gbg fleet and gbg bump run — the dev checkout — so a consumer left behind is found by the owner's next sweep, not by the consumer's own doctor; and a fix pass longer than the window fails gbg fleet until it closes, which is a report, not a block.
  • A tag force-moved on GitHub is caught only through the manifest's git-tree-sha1 disagreeing with the tree Pkg fetched (PIN.TREESHA/PIN.SELF) on the next instantiate; a machine that never re-instantiates keeps the old tree and stays green.
  • The tool's own rounds (D15) grade a moving instrument: the corpus and the instrument share one tree, so a fix to src/ inside a round at the tool root changes the instrument mid-round, which no other consumer can do. The round's head..closed_head range shows exactly that change, gbg release refuses while the round is open, and a round opened off a clean tag is abandon-only (D16) — which is why such a round opens at a prerelease tag vX.Y.Z-rc.<n> (D16's prerelease form) — a report and a refusal, not a gate on the instrument change itself.
