# Shared dev-instrument package for four sibling Julia repos — patterns, sources, and what each dictates

Framing used throughout: the *toolbox* (slash-command `.md` protocols, Workflow JS scripts, Python/Julia/shell verifiers and gates, hat personas, `make.jl` lints, hooks, policy prose) is a **platform**; each of the four repos is a **product** that instantiates it with a small amount of package-specific configuration. Every pattern below is read against that split.

---

## 1. Product lines, commonality–variability, feature models, configuration over code

**1a. Software product lines / commonality–variability analysis.** Canonical: Kang et al., *Feature-Oriented Domain Analysis (FODA) Feasibility Study*, [CMU/SEI-90-TR-21 (1990)](https://www.researchgate.net/publication/215588323_Feature-Oriented_Domain_Analysis_FODA_feasibility_study); Coplien, Hoffman & Weiss, "Commonality and Variability in Software Engineering", IEEE Software 1998; Clements & Northrop, *Software Product Lines* (SEI, 2001).
*Mechanism.* Enumerate the family's members, write down what is **common** (identical in every member, so it lives once in the platform), what **varies** (the variability points, each with its binding time and its set of admissible values), and the **constraints** between variabilities. FODA's feature diagram makes features mandatory/optional/alternative with cross-tree constraints; the product is then a *selection* of features plus values for the variation points, not a modified copy.
*Mapping.* Do this analysis first and write it down as the design document — it is the deliverable that turns "1.5–2× line-count drift" into a list. From the description, the likely result: **common** = every engine (verifier logic, gate logic, recall/coverage computation, seeding, the closure lint, the notation lints, demotion rules), every protocol skeleton, the verdict enumerations; **variable** = package name and description, module list, doc-surface paths, persona *rosters* (which hats are on), package-specific notation patterns, the `julia` invocation, thresholds (allocation slack, tolerance), the list of exemptions. Anything that turned out to differ between the copies but is not on that variability list is *drift*, to be collapsed to one side. Note the survey already recorded in `CLAUDE.md` reached exactly this split ("shared engines, per-package config, per-package `.md`"); FODA adds the discipline of naming each variation point's admissible values, which is what forces the verdict-vocabulary divergence to be resolved rather than merged.

**1b. Feature models as executable configuration.** Canonical: Czarnecki & Eisenecker, *Generative Programming* (2000); Batory, "Feature Models, Grammars, and Propositional Formulas" (SPLC 2005).
*Mechanism.* A feature model is a grammar/propositional formula; a valid product is a satisfying assignment. Tooling validates a configuration against the model before generating anything.
*Mapping.* The per-package config file *is* the product's feature selection, and the platform ships the model as a **schema** (§7) that rejects an invalid selection — e.g. `check-consistency.hats = [...]` must be a subset of the platform's persona catalogue; `bug-hunt.verdicts` cannot be overridden at all because the vocabulary is a platform constant.

**1c. Configuration over code; platform vs product.** Canonical: the "platform engineering"/"paved road" literature (Spotify's Backstage golden paths; Netflix "paved road"), and the SPL "core assets vs product development" split (Clements & Northrop).
*Mechanism.* Products carry *data*, the platform carries *behaviour*. A product never contains a copy of platform code; it contains a pointer to a platform version plus its own parameters.
*Mapping.* This is the single most consequential rule for the four repos: a repo may own **(i)** a config file, **(ii)** a pin, **(iii)** its exemptions ledger, **(iv)** thin generated stubs (§3), and nothing else of the toolbox. The Workflow JS scripts are the hard case — Claude Code's Workflow tool is sandboxed, filesystem-free, configured only through `args` — so they *must* be present per repo as files; make them **generated, header-stamped, hash-checked** copies (§3) whose entire behaviour is parameterised by `args` filled from the config, never edited in place.

## 2. Distributing and versioning shared dev tooling

**2a. The pre-commit model: a hook repo pinned by immutable `rev` per project, updated by `autoupdate`.** Canonical: [pre-commit.com](https://pre-commit.com/); the [autoupdate/rev discussion](https://github.com/pre-commit/pre-commit/issues/1354).
*Mechanism.* Each consumer's `.pre-commit-config.yaml` names a hooks repository and an immutable `rev` (tag or SHA); pre-commit assumes `rev` is immutable and caches on it; branches are explicitly unsupported as pins. `pre-commit autoupdate` resolves the latest tag and rewrites `rev`. The hook repo publishes a manifest declaring what hooks exist and how to run them; consumers only *select and parameterise* hooks.
*Mapping.* This is the exact shape wanted: the shared package is the hook repo; each of the four repos carries one file with a `rev` and its selections; the platform ships a `bump`/`autoupdate` command that rewrites the four pins. Adopt its two rules verbatim: **pins are immutable refs (tags), never branches**, and **updates are explicit commits**, so an instrument change is a visible diff in each consumer's history — which is the "instrument change is a deliberate act with its own commit" rule already on the books.

**2b. Toolchain managers: `.tool-versions` / juliaup pins, side-by-side versions.** Canonical: [asdf](https://github.com/jacobbednarz/asdf) (`.tool-versions` per directory); [juliaup](https://github.com/JuliaLang/juliaup) (channels, `julia +1.12`, `juliaup override set`, project-based selection).
*Mechanism.* Multiple versions are installed side-by-side; a per-directory file selects which one runs, so two projects on one machine can pin different versions without conflict.
*Mapping.* Two uses. (i) Pin the Julia channel the instruments assume (`juliaup override set` or a documented `+channel`), since the CI matrix is already "one Julia, two thread counts". (ii) The same side-by-side principle argues **against** a global install of the instrument package (`~/.julia/environments/v1.x`): install it into each repo's `test/`/`docs/` environment at a pinned version so two repos can be on two versions during a staged upgrade.

**2c. Submodules vs subtrees vs vendoring vs a registry.** Canonical: [Atlassian on git subtree](https://www.atlassian.com/git/tutorials/git-subtree); [adam-p's comparison](https://adam-p.ca/blog/2022/02/git-submodule-subtree/); Go's vendoring model; Julia's registry model ([Pkg registries](https://pkgdocs.julialang.org/v1/registries/)).
*Mechanism.* Submodule = a pointer to a commit in another repo (lean, but a second clone step, detached-HEAD footguns, and every consumer must `git submodule update` after every pull — the sources call the ergonomics "frustrating"). Subtree = the other repo's history merged into a subdirectory (present after clone, no new metadata, but pushing changes back is "clunky" and divergence is invisible). Vendoring = a plain copy plus a manifest recording provenance (what the four repos have now, minus the manifest — which is precisely why they drifted). Registry/package manager = versioned artifacts resolved by a lockfile with compat bounds.
*Mapping.* The four repos sync through Dropbox *and* GitHub, so submodules would break twice (Dropbox does not carry `.git` state reliably, and every machine would need the extra update step). Subtrees hide divergence, which is the disease. **Use the package-manager route for the Julia code (§8) and a manifest-recorded generated-file route for the non-Julia files (§3).** Keep `manifest.py` — as the recorded survey says, it is demoted rather than retired: when two consumers pin different platform versions, the manifest is what detects it.

**2d. Google's one-version rule and how to approximate it across repos.** Canonical: Winters, Manshreck & Wright, *Software Engineering at Google*, [ch. 16 "Version Control and Branch Management"](https://abseil.io/resources/swe-book/html/ch16.html).
*Mechanism.* "Developers must not have a choice where to commit, or which version of an existing component to depend upon." In a monorepo this is nearly free: a third-party library is checked in at one version and everyone uses it. The payoff is that an upgrade is one atomic change with no long tail of consumers on old versions.
*Mapping.* Four separate repos cannot get atomicity, but they can get the *rule*: (i) a fleet-level check (`instruments doctor --fleet`, or simply the platform's README table) that lists the four pins and fails when they differ beyond a staged-upgrade window; (ii) upgrades performed as a **sweep** — bump all four in one sitting, canary first (§6); (iii) no repo carries a local patch to the platform; a needed change goes to the platform and comes back via a pin bump. Julia 1.12's [workspaces](https://github.com/JuliaLang/Pkg.jl/blob/master/docs/src/creating-packages.md) (several projects sharing one `Manifest.toml`) are the in-ecosystem device for one-version *within* a repo — use one to make `test/`, `docs/`, `benchmark/` resolve the instrument package identically inside each repo.

**2e. Semantic versioning and lockfiles.** Canonical: [semver.org](https://semver.org); Julia `[compat]` + `Manifest.toml`.
*Mechanism.* MAJOR for incompatible changes, MINOR for additive, PATCH for fixes; a lockfile freezes the resolved graph so a build is reproducible; compat bounds say what the consumer *tolerates*, the lockfile what it *has*.
*Mapping.* Define what "incompatible" means for an instrument package explicitly, because it is not the usual API surface: **a change in a verdict vocabulary, a demotion rule, a threshold default, a seeded-defect set, or a scoring formula is MAJOR** — it changes what a measurement means (§5). Additive lints and new hats are MINOR. The `rev` in each consumer's config plus the `docs/`/`test/` `Manifest.toml` are the lockfiles; commit the manifests for the instrument environments even though the sub-environment manifests are currently gitignored — the recorded "three envs broken at once" episode is the cost of not doing so.

## 3. Template propagation with updates

**3a. Copier: answers file + template `_commit` + three-way merge on `copier update`.** Canonical: [Copier "Updating a project"](https://copier.readthedocs.io/en/stable/updating/).
*Mechanism.* `.copier-answers.yml` stores the answers and the template ref `_commit`. `copier update` re-renders the *old* template with the saved answers, renders the *new* template, diffs the two, and applies that diff to the working tree as a three-way merge — local edits survive unless they collide on the same lines; conflicts are written inline (default) or as `.rej` files. Files listed in `_skip_if_exists` are generated once and never merged again ("boilerplate"); `_exclude` removes them from management; `_migrations` run version-to-version scripts.
*Mapping.* Copier is the right *model* even if the tool is not adopted: the answers file **is** the per-package config (§7) plus the pin, and `copier update` is the propagation mechanism for the per-repo files that must physically exist (command `.md` stubs, Workflow JS, hooks, the `make.jl` lint wiring, the CLAUDE.md policy block). Its `_skip_if_exists` is the formal name for the "seed once, then the package owns it" class — the exemptions ledger, `CLOSED.md`, `.claude/doc-review-adjudicated.md`. Its migrations are where a verdict-vocabulary rename gets its one-time rewrite script. The caution: three-way merge invites *editing the generated files*, which is how the drift began; pair it with 3c.

**3b. Cruft / cookiecutter: `.cruft.json`, `cruft check`, `cruft diff`.** Canonical: [cruft README](https://github.com/cruft/cruft/blob/main/README.md).
*Mechanism.* Names the disease — "template drift" — and gives it a CI check: `cruft check` exits 1 if the project is behind the template; `cruft diff` shows local divergence from the template; `.cruft.json` records the template commit.
*Mapping.* Whatever tool is used, the **check** must exist and must run in each repo's gate: "this repo is behind the platform" and "this repo has edited a managed file" are both findings. Cruft's exit-1-when-behind is the fail-closed form (§5d).

**3c. Managed files with generated-file headers and hash verification.** Canonical: Go's standard header [`golang.org/s/generatedcode`](https://github.com/golang/go/issues/13560) (`// Code generated by X; DO NOT EDIT.`); GitHub Linguist's [generated-file detection](https://github.com/github/linguist/blob/master/lib/linguist/generated.rb).
*Mechanism.* Every generated file carries a machine-recognisable first-line header naming the generator and its version; tooling (diff viewers, linters, review bots) treats such files as non-hand-edited, and a check recomputes the file from its inputs and fails if the checked-in copy differs.
*Mapping.* Every file the platform emits into a consumer gets `# Generated by GBGInstruments vX.Y.Z from <template> — DO NOT EDIT; edit the platform and re-run …`, and the platform records a content hash per emitted file in the consumer's manifest. The `doctor` (§4d) recomputes and reports `MODIFIED` / `STALE` / `OK`. This is a stronger, simpler guarantee than three-way merge for files the consumer is *never* supposed to touch — which should be most of them: prefer **thin stubs** (a slash-command `.md` that says "run `julia --project=test -e 'using GBGInstruments; check_docs()'` with this repo's config") over rendered protocol text, so nearly nothing per repo needs merging at all.

## 4. Conformance and uniformity enforcement

**4a. Golden paths and scorecards (Backstage / Tech Insights).** Canonical: Spotify Backstage; Roadie [Tech Insights scorecards](https://roadie.io/product/tech-insights/); the platform-engineering [literature review](https://www.frontiersin.org/journals/computer-science/articles/10.3389/fcomp.2026.1814498/full).
*Mechanism.* A golden path is an opinionated, maintained route that is *easier to follow than to leave*; a scorecard is a set of named checks (e.g. "on the current template version", "has the required lints wired", "no expired exemptions") evaluated per component and shown as a level. Conformance is made visible and cheap, not merely mandated.
*Mapping.* The platform ships a scorecard as a command: for each of the four repos, one line per check. This is the fleet view that the one-version rule needs (§2d), and it is the answer to "tractable application to each package": adoption is a scorecard going green, one row at a time.

**4b. Policy-as-code (OPA/conftest) and exemptions with reason, owner, expiry.** Canonical: [conftest](https://oneuptime.com/blog/post/2026-01-28-opa-conftest-policy-testing/view); Rally Health's [policy exceptions](https://rallyhealth.github.io/conftest-policy-packs/exceptions/); [expiring-exception patterns](https://www.systemshardening.com/articles/cross-cutting/policy-as-code-at-scale/).
*Mechanism.* Policies are code, versioned with the platform, and evaluated over structured input. Exceptions are **data**, not policy edits: a registry entry with the rule, the scope, a reason, an approver/owner, and an **expiry date**; the policy treats an expired exception as absent, so a waiver cannot silently become permanent.
*Mapping.* Replace the several ad-hoc escape hatches (`CLOSED.md`, the adjudicated-findings file, the "documented exemptions" in the allocation audit, do-not-re-flag lists in CLAUDE.md) with **one exemptions ledger per repo**, in a schema the platform owns: `{instrument, rule, target, reason, recorded, expires, evidence}`. The lints read it; `doctor` fails on an expired entry and warns on one expiring within 30 days. Crucially this solves the recorded seed/closure contradiction (§5b): a seeded finding is closed by an entry whose `evidence` points at `ground_truth.json` in that round — a file the closure lint reads and the panel preamble does *not*.

**4c. "Exemptions with expiry" as a general contract for enforcement mechanisms.** The CLAUDE.md already states the principle: "an enforcement mechanism with no escape hatch is disabled the first time it is inconvenient, while one whose escape leaves a committed artifact survives." OPA's pattern adds *expiry* and *owner* — the two fields that keep the committed artifact from rotting.

**4d. `doctor`-style diagnostics.** Canonical: `brew doctor` ([design notes](https://www.simplified.guide/homebrew/brew-doctor-run)): checks conditions that interfere with the tool, prints warnings with a nonzero exit, **does not repair**, and says explicitly which warnings are informational.
*Mechanism.* A single read-only command that enumerates every known misconfiguration, names each with a stable identifier, and points at the fix, so a user has one place to look and support has one output to ask for.
*Mapping.* `GBGInstruments.doctor()` per repo: pin currency, manifest hashes, config-schema validity, required lint wiring present in `make.jl`, exemption expiry, environment resolvability (the "resolve/instantiate/LOAD are not interchangeable — only LOAD catches all" lesson belongs here as a check that actually loads), and Julia channel. Read-only; a separate `apply`/`sync` performs changes.

## 5. Measurement integrity for review instruments

**5a. Mutation analysis / seeded defects to calibrate recall.** Canonical: DeMillo, Lipton & Sayward (1978); Andrews, Briand & Labiche, ["Is mutation an appropriate tool for testing experiments?"](https://dl.acm.org/doi/10.1145/1062455.1062530) (ICSE 2005); Just et al., ["Are mutants a valid substitute for real faults?"](https://dl.acm.org/doi/10.1145/2635868.2635929) (FSE 2014).
*Mechanism.* Inject known defects, measure the fraction detected; the detector's recall is only meaningful against a defect population whose difficulty is representative. Andrews et al. found *hand-seeded* faults harder to detect than real ones, biasing recall estimates downward; Just et al. found a significant but imperfect correlation between mutant detection and real-fault detection.
*Mapping.* The seed set is a **platform asset with a version**, and its composition (operator-generated vs hand-seeded, with the real-finding-derived class kept separate) is reported alongside every recall figure, because the two calibrate differently. Recall figures across the four packages are comparable only if they share the seed set version — one more reason the vocabulary and seeds must be MAJOR-versioned (§2e).

**5b. Falsificationism.** Canonical: Popper, *Conjectures and Refutations* (1963); [SEP entry](https://plato.stanford.edu/archives/win2016/entries/popper/): a single counter-instance refutes; no amount of agreement verifies.
*Mechanism.* A claim is admissible as knowledge only if it names what would refute it; a test is an attempt at refutation.
*Mapping.* Already the `/bug-hunt` rule ("only a failing witness is evidence"). The platform should make it *structural*: the witness runner and the verdict enum are platform code, so a package cannot quietly admit a "verified by reading" verdict. Extend it to the instruments themselves: each instrument ships with its **self-check** (their `selfcheck.jl` / `recall_selftest.py` pattern — perturb a copy and require the check to fire), and the check must fail on a fresh clone if its fixture is absent ("the missing case is the failing case").

**5c. Separation of grader and graded.** Canonical: separation of duties (Saltzer & Schroeder, "The Protection of Information in Computer Systems", 1975, "separation of privilege"; auditing practice); in ML evaluation, held-out sets and independent judges.
*Mechanism.* The party producing a result may not also decide whether the result is acceptable; verification is done by a process the producer cannot influence (different code path, different inputs, or a different agent that does not see the producer's rationale).
*Mapping.* Keep the two verifiers with deliberately opposite information (`verify-fixes` sees the diff; `verify` is blind to it), and lift both into the platform so they cannot be "improved" by the session they are grading. Demotion applied **in post-processing by script**, never by the grader — the platform owns that script. The seeded finding must never reach a fix pass or a preamble: the seeds list is readable by the closure lint and unreadable by `panel.js` (§4b).

**5d. Fail-closed / default-deny.** Canonical: Saltzer & Schroeder's *fail-safe defaults* (1975); OPA's default-deny; cruft's exit 1 when behind.
*Mechanism.* Absence of evidence is a failure, not a pass: a missing report, an empty lane, an unknown verdict, an unset required key all fail.
*Mapping.* Encode as platform invariants: a lane returning zero findings is `DEAD`, not clean; an unknown verdict string is a schema error; a gate that finds no round where one is expected fails (this fixes the recorded "IT's untracked findings pile makes the closure gate pass vacuously on a fresh clone" — the platform requires a tracked open-round marker).

**5e. Instrument stability during measurement.** Canonical: metrology's traceability and calibration discipline (BIPM VIM); SPEC's [Run and Reporting Rules](https://www.spec.org/cpu2017/Docs/runrules.html) (a frozen suite, published config, median of ≥3 runs, results outside the rules must be labelled estimates); Goodhart's/Campbell's law for measures that become targets.
*Mechanism.* A comparison across time is valid only if the instrument is the same instrument; change the ruler and you restart the series. SPEC freezes the benchmark suite for years and requires disclosure of everything needed to reproduce.
*Mapping.* "Frozen in-tree at `faa164a1`" becomes "pinned at platform version vX"; a round's report is comparable to a prior round only when both name the same platform MAJOR.MINOR. A vocabulary or scoring change must therefore bump MAJOR and trigger a recalibration run against the seed set before any cross-round rate is quoted.

**5f. Reproducibility stamping.** Canonical: SPEC disclosure requirements; the "stamping" the project already does for benchmark archives (kernel, governor, SMT, …).
*Mapping.* Every findings pile, report, recall figure and benchmark archive carries `{platform_version, platform_rev, seed_set_version, config_hash, julia_version, model_id, date}`. The recorded lesson "a count nothing asserts is a fact about when it was last typed" is the same point: a number without its stamp is not a measurement.

## 6. Contract testing between the shared library and its consumers

**6a. Consumer-driven contracts / Pact.** Canonical: Fowler, ["Consumer-Driven Contracts: A Service Evolution Pattern"](https://martinfowler.com/articles/consumerDrivenContracts.html) (Robinson, 2006); Pact.
*Mechanism.* Each consumer states, as executable expectations, the subset of the provider's behaviour it relies on; the provider's CI verifies the union of all consumers' contracts, so a provider change that would break a consumer fails on the provider's side *before* release.
*Mapping.* Each of the four repos contributes a small contract file to the platform (which config keys it sets, which commands it invokes, which verdicts and report fields it reads, which lints its `make.jl` calls). The platform's test suite runs all four contracts; a MAJOR bump is exactly a contract failure that the maintainer accepts deliberately. This is how the "transparent and maintainable" requirement is met: a platform change tells you which package it affects before it lands.

**6b. Fixture consumer / example project.** Canonical: Documenter's and Aqua's own test suites run against tiny synthetic packages; the "example project" convention of build-tool test suites.
*Mechanism.* The platform contains a minimal fake consumer (a toy Julia package with a `docs/`, a docstring corpus with known defects, a benchmark stub) and runs every instrument end-to-end against it in its own CI.
*Mapping.* This is where the seeded-defect corpus lives *without* touching any real package's docs — the fixture consumer is the calibration bench, which dissolves half of the seed/closure contradiction (calibration on the fixture; real-package rounds seeded only when explicitly requested and closed via the ledger of §4b).

**6c. Canary consumer.** Canonical: canary releases (Humble & Farley, *Continuous Delivery*).
*Mapping.* Upgrade one repo first — the one whose suite is strictest (from the description, PF) — run its full gate, then sweep the other three. The fleet scorecard shows the staged state; the window is bounded (same day / same sweep).

## 7. Configuration schema practices

**7a. Schema-validated config (JSON Schema / TOML), required-vs-optional, fail-on-missing.** Canonical: [JSON Schema](https://json-schema.org); TOML spec; Aqua's own [Project.toml consistency checks](https://juliatesting.github.io/Aqua.jl/stable/project_extras/) as the Julia precedent for validating a config file.
*Mechanism.* The platform publishes a schema with explicit `required` keys, closed enums, and `additionalProperties: false`; a consumer's file is validated before anything runs; a missing required key is an error, an unknown key is an error, and every default is *visible in the schema*.
*Mapping.* One file per repo — `.claude/instruments.toml` (TOML fits Julia's house style and is diffable) — validated by the platform (in Julia, a strict keyword-constructor struct with no fallback for unknown keys does the job without a JSON-Schema dependency; emit the schema document from the struct for humans). Required: package name, module list, doc surfaces, julia invocation, platform pin. Enums: hat names, instrument names. **Forbidden keys**: verdict vocabularies, demotion rules, scoring — those are platform constants.

**7b. Layered config and why it hurts transparency.** Canonical: the Twelve-Factor "config" principle (environment-driven) and its well-known critique in precedence-order confusion (tool docs like pre-commit and Cargo deliberately keep precedence short and documented).
*Mechanism.* `defaults < package < local < env` makes the effective value a function of four places and their order; debugging a mis-set threshold means reconstructing the merge.
*Mapping.* **No layering.** One file, no environment overrides, no local file. Where a machine-specific value is genuinely needed (host name, GPU vendor, thread count), it is read from the machine (`hostname`, `Threads.nthreads()`), not from a config layer, and printed by `doctor --effective-config`. Platform defaults exist only as schema defaults and are materialised into the consumer's file by `init`, so the file is complete and readable on its own.

**7c. Explicit over implicit.** Canonical: PEP 20 ("Explicit is better than implicit"); Google's one-version rule again (no choice ⇒ nothing to infer).
*Mapping.* Every instrument invocation names the config file it read and the platform version it ran; no discovery by directory walking; no "if present" behaviour in the platform except where the schema marks a key optional with a stated default.

## 8. Julia-specific mechanics

**8a. Private registry via LocalRegistry.jl.** Canonical: [LocalRegistry.jl](https://github.com/GunnarFarneback/LocalRegistry.jl); [Pkg registries docs](https://pkgdocs.julialang.org/v1/registries/); [RegistryCI for private registries](https://juliaregistries.github.io/RegistryCI.jl/stable/private-registries/).
*Mechanism.* `create_registry(name, url; push = true)` on an empty private GitHub repo; `register(pkg)` reads `Project.toml` and adds a versioned entry; consumers `Pkg.Registry.add(url)` once per machine (SSH URLs work for private repos), then `add GBGInstruments` resolves like any package with `[compat]` bounds.
*Mapping.* Since the four packages are already private GitHub repos and `GBGIsotropicTurbulence` depends on `GBGPeriodicFields`, a small private registry is the correct home for **all** of them, not just the instrument package — it turns the inter-package dependency into a normal versioned one and gives the one-version rule a `[compat]` expression. Cost: one registry repo plus one `register` call per release; both hosts run `Registry.add` once.

**8b. `[sources]` in `Project.toml` (Julia ≥ 1.11).** Canonical: [Pkg toml-files docs](https://pkgdocs.julialang.org/dev/toml-files/).
*Mechanism.* A `[sources]` table gives a `url`+`rev` or a `path` for a `[deps]` entry; it is consulted **only when that project is the active environment**, so a `test/Project.toml` with `[sources] GBGInstruments = {url = "git@github.com:…", rev = "v1.4.0"}` works, and the docs explicitly mention `path = ".."` in `test/Project.toml` as the intended use.
*Mapping.* The registry-free alternative: no registry to maintain, but the pin lives in four `test/Project.toml` + four `docs/Project.toml` files instead of one place, and `[compat]` cannot express ranges over git revs. Acceptable as the **first step** (it is what `pre-commit`'s `rev` looks like in Julia clothing); move to the registry once the package has more than a couple of releases.

**8c. Test-only dependencies via `test/Project.toml`.** Canonical: [Pkg "Creating packages"](https://pkgdocs.julialang.org/v1/creating-packages/) — with `test/Project.toml` present, Pkg merges package and test projects into the test environment.
*Mapping.* `GBGInstruments` is a `test/`, `docs/` and `benchmark/` dependency, never a `[deps]` of the package proper — it must not appear in a consumer's runtime graph. Julia 1.12 workspaces can make those three sub-environments share one manifest per repo (§2d).

**8d. `Pkg.develop`.** Mechanism: points an environment at a local checkout instead of a registered version. Mapping: for *editing* the platform from inside a consumer during an upgrade (`dev ../GBGInstruments`), then `free` back to the pinned version before commit; `doctor` should flag a dev'd instrument package in a committed manifest as a finding (it is the "local patch" the one-version rule forbids).

**8e. How a shared test-utilities package is normally consumed.** Precedents: [Aqua.jl](https://juliatesting.github.io/Aqua.jl/stable/) (a function called from `runtests.jl`, config via keyword arguments, added to `test/Project.toml`), [ReferenceTests.jl](https://github.com/JuliaTesting/ReferenceTests.jl), [ReTestItems' `@testsetup`](https://juliapackages.com/p/retestitems) for shared fixtures, `Documenter.doctest(Pkg)` as a test-time call.
*Mapping.* The Julia half of the platform is consumed exactly like Aqua: `using GBGInstruments; GBGInstruments.test_all(MyPkg; config = ...)` from `runtests.jl`, and `GBGInstruments.lint_docs(; paths...)` from `make.jl`. The existing lints (`lint_inline_math`, `lint_retired_claims`, `lint_notation_variants`, `lint_review_closure`, the sentence-opener script) become exported functions taking the surfaces as arguments; a consumer's `make.jl` shrinks to `makedocs(...)` plus one `GBGInstruments.lint_docs(config)` call. The method-parity, allocation-audit, pass-audit (`CountingArray`), oracle-registry and public-surface derivation harnesses are the same shape: engine in the platform, frozen baselines in the consumer.

**8f. Documenter-based lint hooks.** Mechanism: Documenter has no plugin API for arbitrary lints, so the convention is plain function calls in `make.jl` before `makedocs`, failing the build by throwing; `doctest = true` and `checkdocs = :exports` are the built-in analogues. Mapping: keep exactly that — the platform exports the lint functions; the consumer's `make.jl` is a managed stub (§3c) so the wiring cannot drift; the "build means `make.jl` exiting 0" rule is then enforced by the platform's `doctor` checking that the stub's hash matches.

## 9. Naming

Julia's own [package naming guidelines](https://pkgdocs.julialang.org/v1/creating-packages/) ask for CamelCase, no "Julia"/"jl" in the name, descriptive over cute, and a name that says what the package does. Ecosystem precedents and connotations:

- **`*Tools`** — the most common Julia suffix for dev-time helpers (`BenchmarkTools`, `DocumenterTools`, `PkgBenchmark`, `TestTools`-style names). Neutral, immediately understood, slightly generic.
- **`*DevTools`** — signals "not a runtime dependency" (matches §8c) and is common in other ecosystems (`vue-devtools`, Rust's `cargo-*` dev-dependency idiom). Good fit; a hair long.
- **`*Instruments`** — measurement connotation, and it is already the house term ("the four instruments", "do not change the ruler"). Risk: in profiling, "instrument" means "inject probes into code" (`Instruments.app`, `instrumentation`), which a newcomer may assume. Since the package *does* also plant seeded defects, the connotation is not wrong.
- **`*Toolkit`** — broad, slightly corporate; fine.
- **`*Assay`** — biochemical "quantitative test of composition"; evocative and accurate for calibrated-recall instruments, but obscure; a reader will not guess what the package is.
- **`*Gauge`** — measuring device; too narrow, since half the package is protocol and enforcement, not measurement.
- **`*Harness`, `*Rig`, `*Bench`** — test-rig connotations; `Bench` collides with benchmarks specifically.

Recommendation: keep the family prefix and the house metaphor — **`GBGInstruments`** — because the CLAUDE.md corpus across all four repos already speaks of instruments, calibration and rulers, and renaming the concept costs more than the mild profiling-connotation risk. `GBGDevTools` is the safe second choice if the package is ever meant to be read by people outside the family. Whatever the name, put the word *instrument* in the docstring's first sentence with the measurement meaning stated, so the connotation is bound rather than assumed.

## Synthesis — what dominates here, and what is a trap

**Dominant patterns, in order of leverage.**

1. **Platform/product split with configuration over code (§1).** Everything follows from refusing to let a consumer hold platform *behaviour*. Each repo ends up with: one config file, one pin, one exemptions ledger, a handful of header-stamped stubs. The "1.5–2× line-count drift" is impossible when the lines are not there.
2. **The pre-commit distribution model, realised with Julia's package manager (§2a, §8a/8b).** Immutable pins, explicit bump commits, a fleet check that approximates the one-version rule. Start with `[sources]` + `rev` (cheap, Julia ≥ 1.11, works today for `test/` and `docs/` envs); graduate to a LocalRegistry private registry, which also fixes the PF↔IT dependency.
3. **Schema-validated, single-layer config (§7).** `additionalProperties: false`, required keys fail, verdict vocabularies *not configurable*. This is what makes the four uniform *and* transparent: the config file is complete on its own and the schema is the feature model.
4. **Measurement-integrity rules as platform invariants (§5).** Versioned seed sets, MAJOR bump on any change to a verdict, demotion or score; stamps on every report; grader/graded separation enforced by where the code lives (platform) rather than by discipline; fail-closed on absence. This is the part the current in-tree copies cannot deliver at all, because the ruler lives beside the thing it measures.
5. **Contracts + a fixture consumer + a canary (§6).** The fixture consumer is the calibration bench and the home of the seeded corpus; the four contract files tell the maintainer what a platform change breaks before it ships; the canary bounds the blast radius of a sweep.
6. **`doctor` + scorecard + expiring exemptions (§4).** The adoption path *is* a scorecard going green per repo; the escape hatches that keep enforcement alive are one ledger with reason/owner/expiry, which also resolves the recorded seed-vs-closure contradiction (seeds are evidence-backed ledger entries readable by the lint and invisible to the panel preamble).

**Traps.**

- **Layered configuration.** `defaults < package < local < env` looks flexible and destroys transparency; every "why did this threshold apply" becomes archaeology. One file, no overrides, machine facts read from the machine.
- **Git submodules.** Two-step clone, detached HEADs, silent staleness, and a Dropbox-synced tree — the ergonomics fail here on three counts. Subtrees are worse in a different way: they hide divergence.
- **Template-with-merge as the primary mechanism.** Copier's three-way merge is excellent for the few files that must be seeded and then owned by the consumer; used for everything, it invites hand edits to rendered protocol text, which is exactly how the drift arose. Prefer thin stubs + hash-checked generated files; reserve merge for `_skip_if_exists`-class files.
- **A "shared" package that still lets consumers override the vocabulary.** If verdict enums, demotion predicates or scoring are configurable, the four will diverge again inside the schema instead of outside it. Make them constants; make changing them a MAJOR release with a recalibration.
- **A global install** (`~/.julia/environments/v1.x`). Breaks side-by-side versions during a staged upgrade and hides the pin from the repo. Install per environment.
- **Untracked findings piles + a closure gate.** A gate that finds nothing and passes is the antipattern the corpus already names; the platform must require a tracked open-round marker or fail.
- **Improving the instruments while a round is running.** Already ruled; the package structure makes it enforceable — a round's stamp names the platform version, and a version bump mid-round is a visible violation.
- **Over-generalising on day one.** Two consumers (PF and IT) already have concrete divergences to resolve (demotion by emptiness vs by content — the emptiness rule won on evidence; staleness from mtime, with the default-direction rule stated beside it; the verdict sets). Resolve *those* in the first release with the four contract files as the acceptance test, and let the other two packages adopt by scorecard rather than designing for a hypothetical fifth.
