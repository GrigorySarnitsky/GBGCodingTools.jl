RULE.DOC.ARGCOV (.gbg/policy/docs-rubric.md:44-49)
  Statement: "Every argument in a docstring's signature, positional and keyword, is named as code in its body."
  Why: "A reader passing an argument the docstring never mentions has to read the source to learn what it does."

Reading applied: "named as code" = the argument's name appears in an inline code span (single backticks) in
the body of THIS docstring. A name inside a longer code span (`merge!(into, from; weight)`) counts. A name
appearing only in math (``x``, \texttt{weight}), only in prose ("the summary"), or only via a cross-reference
("Arguments: as for [`other`](@ref)") does not. A coincidental identifier in a jldoctest block (`h = Histogram1D(...)`,
a histogram, not the bandwidth keyword) is not the argument being named.

Reported line: every finding points at the opening `"""` of the unit's docstring (the signature is on the next
line). Since the defect is an absence there is no body line to point at; the docstring opening is adequate.

TOTALS: 80 findings; 78 TRUE, 2 FALSE. All 80 reported lines point at the unit's docstring (its opening `"""`).

Pattern the check missed (the 2 FALSE): an argument named inside a LONGER inline code span, here the call form
`merge!(into, from; weight)` — the check evidently matches only a span whose whole content is the bare name
(`into` is such a span in the same docstring, and was not flagged).

Patterns behind the 78 TRUE, for the caller:
- 15 docstrings delegate with "Arguments: as for [`other`](@ref ...)" (18 of the 20 flagged units are
  *_standard_error / *_with_standard_error companions of a documented estimator). The rule as written does
  not accept a cross-reference as naming, so these are TRUE under the letter; whether a delegation should
  satisfy ARGCOV is a question for the rule, not for the findings.
- `summary` is flagged in 19 of the 20 units: the receiver is written in prose ("the summary") and never as code.
- Names that occur only in math (``x``, ``g(Y)``, h_z, \texttt{weight}) are not code. Note the check's own
  leniency in the other direction: it did NOT flag `x`/`z`/`g` where they appear as ``x`` (Julia-Markdown
  math, rendered as $x$), so it reads a double-backtick span as code; by the statement those are not named
  as code either, and strictly a few more findings would be due (e.g. `x` at ConditionalDensity.jl:228,
  `kernelz` at ConditionalExpectations.jl:558).
