GBGCodingTools — architecture

Written by AI, not regularly reviewed

This page is written by AI and is not reviewed regularly by a human.

This is the target design, and it is normative: code that disagrees with it is wrong, or this document changes first. It follows the owner's rulings; no question about it is open. A term in bold is defined where it first appears, and the reason for each mechanism is given in brackets: a requirement R1–R10 from the owner, or a failure seen in the past. R11 asked for a short normative architecture in plain words: this document is its whole answer. Not in it: the migration order (IMPLEMENTATION.md); history and the replaced architecture (git's history).

1. Purpose and scope

GBGCodingTools is a Julia package, on the Julia 1.12 floor. It keeps the owner's Julia packages written to one set of rules, and it helps AI sessions find and fix defects in them without breaking how they work. It serves the four science packages — GBGPeriodicFields, GBGHomogeneousTurbulence, GBGStreamingStatistics, GBGCloudPhysics — and itself. Each of the five is a package below; the owner is the person who owns them; a session is one Claude Code conversation working in a package. GBGCodingTools is also called the tooling package here.

It does four things:

  1. It holds the rulebook: every rule on how documentation and code are written, each a Julia value carrying its statement, the check that decides a violation and, where a program decides, examples that break and comply [R5, R7].
  2. It runs the rules' program checks inside each package's documentation build and test suite, always [R7].
  3. It provides instruments: procedures the owner asks a session to run, which find defects. Documentation defects are fixed without the owner and the fixes are checked; code defects are put to the owner [R1, R2].
  4. It generates every file that connects a package to GBGCodingTools, so the five carry the same files [R6].

It is not: needed by anyone who only uses a science package (it is a developer-side dependency, §5.1); a reviewer that runs unasked, apart from the one audit an approved fix carries with it (§4.4); a place for plans or history; and not a defence against a session that forges files. It guards against honest, overconfident mistakes: a program, not a session, decides whether a change is safe and when work stops.

A finding is one reported defect with every place it occurs. A run is one execution of one instrument on one package. An agent is a model instance a session launches to read and report. A failing test is a small test, written by an agent, that fails on the package as it is. Careful is the most capable model, and every reader of a review runs on it [ruled 2026-09-20]; Strength stays a per-agent setting, FULL or ECONOMY. Every gbg command exits 0 (nothing found), 1 (findings), 2 (cannot evaluate) or 3 (crash); no verdict is read from a log, and no check's output is shortened.

2. How the checks and instruments differ

The owner's three distinctions are used, each with one value per check or instrument [R3, R4]:

  • Intention — what the defects it looks for are in. Documentation: docstrings, comments, hand-written pages and rationale documents, as §4.2 lists exactly. Code: everything else, including stored data that code reads. The future leak scan alone has a third value, publication, because a leaked password is neither [R8].
  • Decided by — who says a finding is real. A program; an agent proposes and a program decides (the agent writes a failing test, and the finding exists only if GBGCodingTools runs it and it fails); an agent, quoting it.
  • How found issues are fixed — by whoever ran the build or test, as ordinary work; the documentation fixer (automatic, checked); the code fixer (only on the owner's answer, checked); regenerated; by the owner only.

No two rows of the table in §3 have the same three values; test/architecture.jl reads those three columns from ALWAYS_ON and INSTRUMENTS and fails on a repeat, and no further distinction is needed to separate them. The last two columns are fields of the same values (§5.2) — an always-on check has no run, so its ending is a dash — and the test compares the whole table. Every rule has one of three covers (§7): a program, a reader, or an instruction the session follows. A rule a reader judges belongs to exactly one reader, or the run reports it as a gap; a rule naming a discipline belongs to that discipline's reader; a question-language rule to §8's one agent.

3. The table

Always-on checks are programs run by every build and test; nobody starts them and they have no runs [R7]. What they find is fixed by whoever ran that build or test, as part of the work in hand: no run, no verifier, no question. Instruments run only when the owner asks, in words or by slash command (as ruled), with the one exception §10's start rule writes down. The two fixers exist only for what an instrument found. An instrument's name says so: a check is always on, and a review, hunt, audit or scan is an instrument the owner starts; a new one is named the same way. Inside the code the word "check" keeps its ordinary meaning (Rule.check, Questions.check, gbg docfix check), and names nothing that runs on its own.

A Change audit starts by itself in exactly one place: once, over an approved code fix that has gone green (§4.4) — superseding the earlier ruling that an audit was only advised, since the owner asked to be told not just that a bug was fixed but how well. It never audits its own follow-ups, and §10's start rule carries the exception in full. Documentation review and Bug hunt can meet one disagreement between a docstring and its code from opposite sides: the review compares, the hunt reports only what a failing test shows; either way a possible code defect reaches the owner as a question, and an answered question never returns (§8).

Two rows are marked future and are built only when the owner asks: the Bug hunt and the Change audit, deferred on 2026-09-21 so that the documentation half reaches the four science packages first. Deferring them defers the code fixer with them, and with it the one place an instrument starts itself — an audit over an approved code fix — so until they are built nothing in this package changes code, and a code defect an instrument meets is what it already was: a question to the owner. The table test (§6) reads a row marked future as exactly an instrument not built, which keeps no skill file and refuses to start.

The leak scan, future from the start, was built on 2026-10-02, before the packages go public: its rules, a reader of every branch, commit, message and manifest, its Instrument value and the PUBLICATION intention. Its design is §3.1. It writes no tracked file: no run record, report or work-queue line. Its findings are printed in the session that ran it, where the owner reads them and acts. Guard.refuse_publication is called by every writer of a tracked file — run record, report, question store, settled rulings, work queue — and exits 2 on text from a publication run.

3.1 The leak scan's design

Decided by the owner on 2026-10-02, before the packages go public.

The content of every commit, on every branch and tag, deleted files included, is read by Gitleaks: a pinned release, checked against its published checksum. Its default credential rules run, and this package's own rules are rendered into its configuration from their values, so a pattern has one home.

This package's rules name what no generic scanner knows is personal here: home and Dropbox paths, the machines' names, an email address not on the list the owner approves, a session link, a scratch path, an absolute path in a manifest, and a file that is never published, by its name or kind.

The commit metadata — authors' and committers' names and addresses, commit and tag messages — has its own reader, through the same rules, because Gitleaks reads patches only. The GitHub side — issues, pull requests, comments, release notes, workflow logs — turns public with the repository and is not in git; it is read through gh on a flag, the one part that needs the network.

Every finding is redacted. It names the rule, the commit, the file and line and a fingerprint, never the text: a finding printed in a session enters what that session sends to its model. A false positive is a Switch with its reason.

Three tiers (the owner, 2026-10-02: a machine's name in the history is no threat, a credential anywhere is). A credential or a file never published is blocking, fixed and never accepted. A note — a path, a word, an address, a link — that the default branch's files hold is cleaned when it is cheap. A note only the history holds may be accepted: gbg leak --accept records its fingerprint in .gbg/leak-accepted.txt, which holds hashes alone, and a later scan counts it as accepted.

Not used: a scanner that verifies a secret by trying it, which sends the secret out, and any Python tool. Removing a leak from history is a rewrite the owner makes, outside the instrument.

4. Finding and fixing

FINDING PARTS                        FIXING PARTS
Documentation review ─┐              ┌─ about documentation ─► DOCUMENTATION FIXER ─► guarded commit
Bug hunt ─────────────┼─► collect ───┤     ─► checks ─► verifier, blind then with the diff ─► closed or open
Change audit ─────────┘              └─ about code ─► question ─► the owner's answer, with any direction:
                                          "fix the code" ─► CODE FIXER ─► attempts until green (3 at most) ─► commit
                                               ─► ONE CHANGE AUDIT ─► its grade and concerns to the owner
                                          "fix the documentation instead" ─► DOCUMENTATION FIXER
                                          "not a defect" ─► optionally recorded as settled (§8)

An always-on check has no run: a red build or test is fixed by whoever ran it as part of the work in hand, and the wiring check's answer is to regenerate (§3). The two fixers below are for what an instrument found. Finding and fixing are separate parts [R1]: a check or an instrument finds and hands what it found to a fixer, which fixes. What keeps them apart is who does the work — a fix is graded by agents that did not find the defect and are not told how it was fixed (§4.3 step 5), or by an audit that found neither (§4.4). A fix pass is a stage of a run and spends its budget; the judgement of that pass belongs to someone else.

Why only agent findings are rationed. When a program decides, fixing may repeat until the check passes, with no limit: the check is the same question every time, answers the same way on the same input, and says itself when the work is done. When an agent decides, a fresh reading of edited text is a new opinion, not the same question again, and nothing guarantees it ever reports nothing: hence one search per run, at most four fix passes, and whatever is left carried over [reviews re-reading after each fix ran 9 and 15 passes without settling]. The code fixer's three attempts (§4.4) are not this rationing: they are a judgement about the fixer, not about the loop.

4.1 Finding, and the handoff

Agents write one result file each into the run's scratch directory (.gbg/scratch/<run>/, §11) and nothing else: collect turns those files into findings and exits 2 when a tracked file changed while agents ran. An agent whose file is missing or malformed is relaunched once, then named in the report. Collect gives each finding an id and fixes the list, so a run never searches twice, and anchors every location (§4.5): the agent gives the file, the quote and, where it knows it, the node; the program fills in the rest, including the line, which it never takes from an agent, and a quote it cannot find is named in the report and given to no fixer. A location in a declared build-time copy (§6) moves to the same node and quote in its tracked source when the copy is identical to it, and is otherwise dropped and reported [fixes landed in a copy the build then overwrote].

A finding goes to the documentation fixer when its instrument's intention is documentation and its agent did not mark it as a possible code defect; otherwise it becomes a question. The change guard has the last word (§4.2).

4.2 What is documentation, and the change guard

Documentation is exactly: docstrings and comments in .jl files under src/ and ext/; hand-written Markdown under docs/src/; README.md; the rationale documents the config names; the CLAUDE.md sections its claude_documentation names, when no other line changes [facts, not instructions; ruled 2026-09-29]; and, in GBGCodingTools, a Rule's statement and why. Everything else is code [R2]: other .jl files whole (tests, docs/make.jl, Literate scripts, whose comment marks decide what runs); Project.toml and Manifest.toml; the config; stored data code reads; every generated path and declared copy (§6); CI, hook and skill files; the rest of CLAUDE.md; a document the config declares normative, which wins over "rationale" [a fix aligning a specification with code would authorise that code]; and every other part of a rule, agent role, discipline or instrument — id, check, examples, parameters, file sets, tags, strength, lists.

The change guard is the program Guard.classify(cfg, path, before, after, generated), where generated is what that path's generator produces now, or nothing where no generator writes it. The caller supplies it: the guard lives in Engine, which may not reach Render (§5.1), so the verb holding the generators — gbg docfix commit, and the wiring check — regenerates and hands the text in, and no layer below CLI calls a generator [as ruled]. The guard returns documentation only when all of these hold, and code otherwise:

  1. a generated path or declared copy whose new content is exactly generated is left out of the classification: it merely follows whatever else the commit changed, and any other content there is code. This is what lets a reworded rule statement be committed with the policy files it feeds (§4.3 step 2);
  2. the path is on the documentation list;
  3. for .jl: both versions parse, and they are byte for byte the same, whitespace included, except the TEXT inside docstrings the file already has and the text of comments it already has [the simple rule, ruled 2026-09-23]. A docstring or a comment is never added, removed or moved by the fixer: a missing docstring comes to the owner as a question with the proposed text. A docstring's text is the string tokens of a string the parser attached as one, anywhere but inside a quote or a macro call's arguments, where a string is data (Base.@kwdef excepted, unless the file defines its own). In a Literate example a Markdown line (# then a space, or # alone) and a code comment (##) may be turned into each other, which decides only whether the comment shows on the page [ruled 2026-09-24]; a mark or a #= block stays exactly as it is, and a prose run may not leave a fence open (clause 4 lives here). A file that reads its own line numbers keeps every line break. [Every earlier guard judged when a docstring's presence or a comment's place changes what loads, and five review passes found fifty ways past those judgements; with structure fixed there is nothing to judge. Measured on GBGPeriodicFields: 231 reworded docstrings refused 0 times; its 51 real fix commits refused only where mathematics changed.]
  4. in GBGCodingTools only, differences confined to plain string literals given to the keywords statement or why of a Rule(…) call are documentation — any number of them, in any number of files — with the parsed trees identical at every other node; a moved, added or removed argument, a changed id, check, example or parameter, or an interpolated string in those fields, is code;
  5. in a Literate example, no mark, separator or #= block moved or changed (decided within clause 2);
  6. in every removed docstring and every changed page, every fenced block whose info string starts with jldoctest or @ is identical, info string included, and in the same order — as Julia's Markdown parser reads the page, each string literal's value and each Literate comment (so in a blockquote or a list item too), and as found by pattern in the text, a change either sees being refused — doctest input and output, @example, @eval, @setup, @meta, @raw, and the signatures and filters of @docs, @autodocs, @index and @contents.

Clause 3 is narrower than "the prose of a rule and of an agent role". An agent role's or a discipline's description, like the question of a rule an agent checks, is an instruction to an agent: rewording it changes what the instrument looks for and no program compares it with anything, so it stays code. A rule's statement is read by agents too, so it is not simply documentation either: it is the one code-like text the fixer may touch, and only under §4.3 step 3, listed in the report.

A file that reads its own line numbers is code whenever a line moved: a longer docstring shifts what @__LINE__ or a macro's __source__ returns [until 2026-09-23 an accepted limit; the review showed it changes a value the program reads]. test/guard.jl holds one example per clause, in both directions [parsed code alone passed changed doctest output, a @autodocs filter, and a docstring that stopped a call from running]. For clause 3: two reworded statements and a reworded why in one file (documentation); a changed check, id, tag or argument order, an interpolated statement and a reworded description (code); and the same rewording outside the tooling package (code).

4.3 The documentation fixer — automatic, with checks

The documentation fixer is the session on the careful model, working through gbg docfix steps. It starts only inside a run the owner asked for, and then fixes and verifies without asking again [R1, R2].

  1. Re-anchor, then other copies. Every pass begins by re-anchoring the open findings (§4.5); a location that comes back OUTDATED is named in the report and not worked on. A program then searches every documentation file for the finding's quote and each formula in it, adding every hit as a further location, anchored like the rest [a fourth copy of a corrected formula survived a fix].
  2. Guarded commit. The fixer edits, then gbg docfix commit regenerates every generated part whose generator reads the prose that changed — the policy files and the tooling package's block in CLAUDE.md — and classifies every changed path in the working tree with the change guard, which leaves those regenerated parts out by its clause 0. It commits all of them on the current branch if every classified path came back documentation and no documentation rule the run opened clean on breaks, else exits 1 and commits nothing; it warns of a cross-reference it cannot resolve, refusing nothing on that; the session then pushes. The build runs once per pass, at gbg run next, and a red one names the pass's commits that touched the files it complains about [ruled 2026-09-26]. This is the one verb that commits, because the guard must run before a commit exists, replacing the old rule that no verb commits [a code edit committed before the guard ran would be pushed].
  3. Formula and rule-statement edits. An edit that changes mathematics is never made automatically. Mathematics is what Documenter renders as a formula: whatever Julia's Markdown parser reads as one — a double-backtick span, a fenced math block, a dollar-sign span or display — in a page, a docstring or a Literate comment, and nothing else [ruled 2026-09-23: the rule protects rendered formulas, not every spelling of one]. A symbol, number or sign changed, a formula added, removed, reordered or moved to another docstring are all changes; respelling an inline code span as a math span with the same text, in the same place, is not. A formula the parser reads but that does not render — a broken brace — is still mathematics: fixing it is the owner's: the change guard refuses it (clause 6) and the finding becomes a question for the owner [ruled 2026-09-21]. The rule considered before that, and declined, was an automatic edit backed by a quote from the documented method's body plus a numeric check the program ran; the reason it was declined is that both halves make the CODE the oracle, so code that is itself wrong certifies prose matching it, and the tool would be executing Julia an agent had just written. A reworded rule statement (§4.2 clause 3) stays automatic but is verified blind on the careful model, the verifier being given the rule's check and its examples, because no program compares a statement with the check it names. Both kinds are listed in the report [a docstring was "fixed" to contradict code that was itself wrong; a fix wrote false mathematics]. A finding whose fix only the owner may make — the config, code, a formula — is PARKED by the fixer with gbg run park <id> --why "…": the same question a HIDES_CODE_DEFECT puts stands on it, no pass or verifier works on it, and his answer does what it does there [ruled 2026-09-24; left open, such a finding cost a verifier every pass and reached the owner only at close].
  4. Checks. gbg docfix check runs the documentation checks, doctests and docs build; a check that passed at the run's first commit and fails now is exit 1.
  5. One verifier per place, with the diff. gbg run next re-anchors the findings (§4.5) and writes the verify stage's arguments from the anchors it got, so the text a verifier is sent is the text the findings are about. The open findings are grouped by the unit they sit in — the built page, for the withheld reader's; the example's source, for one made on it; the file named first, otherwise — and ONE verifier per unit (at most ten findings each) is given those findings, the unit as it now stands, what the reader that found them was given (§5.3), and the diff of the pass's commits, oldest first, and answers each finding by id: FIXED, NOT_FIXED, LINE_ONLY (fixed at some locations only), MADE_WORSE (the change broke something the old text had right), HIDES_CODE_DEFECT (the documentation now describes code that looks wrong) or NOT_A_DEFECT, each with one verbatim quote. It runs at the tier of the reader whose findings it judges. [Until 2026-09-26 a blind verifier per finding ran first and a second read the diff for what it called fixed. Measured on GBGPeriodicFields' first full run: 187 verifier launches paid the same ~146k tokens of fixed context each, nine times the cost of finding; the blind stage was wrong on 47% of its not-fixed verdicts, since a fix by linking a term is invisible with links stripped and a quote of two spans joined by "…" is in no file; the diff stage made the one real catch. Ruled: one verifier that sees both, per place.]
  6. Grade. A program applies the verdicts. Every verdict except NOT_FIXED needs a quote the program finds in the current text, each "…"-separated span on its own, or it becomes NOT_FIXED, the demotion written on the DocFix; so is a finding no verifier answered for. MADE_WORSE reverts the pass's commits for the finding; HIDES_CODE_DEFECT reverts them and asks the owner — unless he already answered "fix the documentation instead", when the edit stands and is listed. A NOT_A_DEFECT closes the finding for this run, listed but never stored.
  7. Passes. One by default [ruled 2026-09-26: a second pass over unchanged text moved 22% of the verdicts by variance, at a third of the first pass's cost; four was the cap before]. A fix stage that committed nothing closes the run, and what is still open goes to the owner's queue.
  8. Cost. gbg run cost <dir> sums each agent's own usage records from the launch's transcripts and writes them on the record per stage and pass; the report prints them. The launch's summary field counts a tenth of the cache activity, where nearly all of the cost is, and is not used.

4.4 The code fixer — only on the owner's answer

The code fixer is the session making a code change the owner asked for [R2].

  1. Approval, and direction. A code finding becomes an item of a question (§8) and nothing is touched until the owner answers "fix the code"; a run's code findings form one question with an answer per item [a hunt confirms 9 to 21 defects]. The answer may carry the owner's direction — how he wants it fixed — recorded with the question, handed to the fixer, and handed to the audit as part of what the change is measured against.
  2. Attempts, on the deterministic oracle. The fix then repeats until the failing test goes from failing to passing and Pkg.test() and the docs build are green; it may loop because the oracle is the same question every time and answers the same way (§4), so it ends by passing. Three guards: the failing test is frozen for the loop and an attempt that edits it does not count [weakening the test is the cheapest way to pass]; any change under test/ is named first to the audit [a fix that also edits the test that would have caught it is the shape an audit exists for]; and after three failed attempts the loop stops and the attempts, with what each failed on, go to the owner as a question [in the owner's words: if the same problem is not fixed in three attempts, there is reason to believe the fixer cannot fix it cleanly — a judgement about the fixer, not the budget of §4].
  3. Commit. The change is committed on the current branch and pushed; there is no separate branch. The failing test of a question the owner has not yet answered is committed by gbg run close into test/regressions/escalated/ — the one code path a run may add to, since nothing there is run or referenced and a witness left in scratch is lost. Pkg.test() never runs that directory; on a green fix the code fixer moves the test unchanged into test/regressions/, and on any other answer deletes it.
  4. One audit, and a grade. A Change audit then runs once over that change, without the owner asking. It is given the finding, the owner's direction and the diff, and returns concerns and a grade: whether the change was no wider than the defect and that direction, whether it changed a default or a documented contract, and whether input that worked before still works [an audit caught two regressions the failing tests missed]. Both reach the owner with the fix, in the CodeFix kept with its question (§5.2) — in the run record when the question came from a run, in the question store otherwise — and in the run's report: not only that it is fixed, but how well.
  5. No recursion. The audit never audits its own follow-ups: a concern the owner wants fixed is a new question, and on his approval it loops as above and gets its own single audit. Nothing chains on its own and every step waits on an answer [fix → audit → fix, each audit fixed inside the next, is the loop that had to be stopped].

4.5 Where a finding is, while the text moves

A line number is not a place: a fix earlier in a file moves every line after it, four passes compound that, and a carried finding's lines were read at an older commit, so a stale number points at whatever now sits there — which is how a fix lands in the wrong paragraph. So a location (§5.2) is the file; the node — for .jl the binding or method documented, or the field of a constant when the text is a generated docstring (ARGS_FORM.statement), for Markdown the heading path, empty where there is none of these; the quote, the decisive text as it read then; and the line, kept only as a hint.

Re-anchoring runs before each fix pass, before each verifier stage, and when a finding is carried into a later run. Texts.reanchor does the two steps that need only files: the node — parse the file with Julia's own parser (JuliaSyntax, part of Julia 1.12) and find the named definition, or scan the Markdown headings — and then the quote inside it (BY_NODE); failing that, the quote alone, nearest the old line when there are several (BY_QUOTE). A quote is compared with the source as both READ on the built page (Texts.reading): markup the page renders away — link targets, backticks, dollars, emphasis, a docstring's escaped backslash, Literate's comment marks — is taken from both, and whitespace flattened, so a quote copied from the page, or one the source wraps, is found in its file. Runs.reanchor is the wrapper a run calls: it tries Texts.reanchor first and, when that fails, maps the old line by git through the changes since the line was read (BY_DIFF) — which is why the git step lives there, not in Texts (§5.1). A location records the commit its line was read at, so a line found again on a later pass is not carried through the same diff twice; a line of 0 was never a place, and is not mapped. If all three fail the location is OUTDATED, never pointed at whatever now sits on that line: the report names it, the fixer is not sent there, and a verifier that needs it is given the file's changed regions.

5. The Julia object model

5.1 Modules, types first

Each module uses only the modules above it. A rule's check may use only Model and Texts, which is why rules sit beside their checks in Catalogue, above the machinery that runs them. What executes inside a consumer's build or test — the harness and the makedocs wrapper — may not reach Orchestration, where run records live; the tooling package's own test files may, since they test it. test/architecture.jl parses the sources and fails on any reference, qualified or imported, that breaks either rule.

Model          every struct and enum; no values, and no behaviour but `relocated`, the one copy of a draft
Texts          reading docstrings, pages and the built site, given a Config value; anchoring by node and quote
Catalogue      RULES (src/Rules/*.jl, each rule beside its checks), INSTRUMENTS, ALWAYS_ON, DISCIPLINES, RETIRED,
               the reader derivation (Roles), the Cover enum — data
ConfigIO       the literal-only readers of config.jl and settled.jl; validate
Engine         Checks (applies), Harness, Guard, Questions.check's programs   ← the harness reaches no further
Render         the generators, GENERATED and the wiring check                 ← the makedocs wrapper reaches no further
Orchestration  Agents (arguments), Runs, and Runs.reanchor's git step
CLI            the gbg verbs, each a function returning an exit code

What must be Julia, and what may be borrowed. The skeleton is Julia because of what it is for: the types, the rules with their checks and examples, the agent roles, the instruments and the generators are what the owner reads, what Documenter renders on the package's own site, and what its own instruments read when pointed at it; a rulebook in another language could be neither reviewed as values nor checked by the machinery it describes. Beyond the skeleton there is no thrift: packages and external programs are used wherever they do the job better, which replaces the older rule of no Python and no child process beyond a few named commands, still carried in CLAUDE.md [as ruled].

One boundary stays: whose dependency this is. GBGCodingTools is a developer-side dependency: it lives in each package's docs/ and test/ environments, which gbg sync writes, and never in the package's own [deps], so ]add GBGPeriodicFields pulls none of it and no user of a science package resolves it. What it brings — JSON3, Gumbo and the rest — is paid for there, by the developer. What runs inside a consumer's build or test stays offline and reads no git or review state, because CI and a fresh clone must answer alike; a child Julia process is allowed [2026-09-27]. Readers are derived, not listed [ruled 2026-09-20]. A rule no program decides carries access — what a reader must be given beyond the unit it is about: NOTHING (exclusive: the unit alone, since more would change the answer), SIBLINGS, OTHER DOCUMENTS, SOURCE, RENDERED, HISTORY, CITED WORK, or a combination — put on from the rule's own text by three blind readers (§12), and, where its own words are a field's, discipline. Roles.derive computes the panel: three bound readers, one per bundle of material a rule lands in, tried in order — withheld (one built page or Literate file alone), full (siblings + source + other documents), rendered (the built site) — a rule going to the first bundle that covers its need; one reader per discipline the package declares in Config.disciplines, an open expert reading the whole documentation for what is wrong in its field, bound only to a rule naming that discipline; and two open standpoints with no rule, plain_sense on one page and logician on the whole [the two highest yields in the one review that recorded them]. A rule no reader can be given, and a rule naming an undeclared discipline, is a gap, printed at every launch and first in the report; there is no fallback, because a pass from a reader that cannot recognise the defect is indistinguishable from not looking. The three bundles, the two standpoints and the discipline catalogue are the hand-written mechanisms (§13); a package writes none — one it needs and the catalogue lacks is requested from the tooling session. Every reader runs on the careful model; gbg run … --readers bound|open|both chooses which are launched, bound by default. An open reader's findings name no rule, so the reason for trusting it is its standpoint, and a finding that recurs becomes a rule (§7).

Targets and material [ruled 2026-09-23]. What a reader is GIVEN is decided by audience, not by file type. A target is what a user reads — a docstring, a hand-written page under docs/src/, a Literate example, and the one document architecture_doc names — and is the only place a finding may be located and the only thing the fixer is ever handed. Material is what a reader may open to judge a target and never report on: the source, every rationale document that is not a target, and every generated page; a reader is GIVEN a material document only when the package lists it in Config.material, empty by default. Every other rationale document is read by nobody unless listed: not launched over, not handed to the full reader or a discipline, not walked on the site — the site walk keeps only a page whose source is a target, so a build-time copy of the working notes drops out by construction. A finding located only in material is kept, marked in_material at collect, reported in its own section and routed to the owner, unfixed and unverified [it may be the formula three docstrings copy]; gbg docfix commit --finding refuses an edit to such a document. Program checks are untouched and run over the file sets they declare. Catalogue.target is the one predicate, and a change to a non-target rationale document reaches no reader under a changed scope. [On GBGPeriodicFields the full reader and each discipline had been handed four working-notes documents, ~164,000 tokens, under two rules that had that day been ruled not to apply to them.]

Rule docstrings. Each Rule, AgentRole and Instrument constant gets its docstring from doc(x), attached by a @doc doc(x) x call in the source. The rule that source docstrings match the loaded module's compares only literal docstrings, and requires every other docstring in the module to come from such a call, found in the source. 5.3 What becomes Julia

The rule prose, the rule register and the scan catalogue become Rule values beside their checks, the fixture's defects their Examples; the tags on the rules and the discipline catalogue become the readers, derived at run time, the hats' briefs surviving only as the two open standpoints and the disciplines' descriptions; instrument protocols and Workflow scripts become Instrument values, Runs stages and one fixed driver; JSON schemas become Julia constructors, with agents' output schemas generated from the types; config.toml and the exemptions ledger both become config.jl, an exemption being a Switch there, while settled.jl is new and holds only the owner's rulings; templates and managed.json become Render generators and the GENERATED registry.

7. Deterministic first

When an agent may check a rule [R7]. Only when deciding it needs the meaning of a sentence (is this claim true of the code), a derivation (is this formula right), or a document read in order (is this term defined before its first use) — the three WhyAgent values. Whatever a pattern, a parser, reflection on the loaded package or the Documenter build can decide is a ProgramCheck from the start; that includes a docstring's stated defaults and argument names against the signature, and docstrings in the source attached to nothing [five such went unfound]. A partly decidable rule splits into a program rule and an agent rule. Every rule has one of three covers, read off the rule (Catalogue.cover): a program; a reader, given the material the rule's access tag names; or an instruction the session follows while working — how to commit, what to run unasked, how to read what a scan prints — checked by nothing and saying so in unchecked_reason. A statement about how this tool itself behaves is this document's, not a rule [ruled 2026-09-21]. The rules page groups the rules by cover.

A check is shown to match its rule by test/rules.jl (§5.2). Bug hunt can also be pointed at the rules, where a failing test is a text the rule forbids but its check lets pass, or the reverse; only the owner decides what a rule means, so each becomes a question, and on "yes" the text becomes an example and the code fixer changes the check.

A recurring agent finding becomes a program check. Each verified documentation fix leaves its commit — the text before, which broke the rule, and after, which complies — in the run record, and the report lists the fixes per agent-checked rule. When a rule recurs, the session proposes a program check as a code change; those pairs are its first examples, and test/rules.jl must pass on them.

8. Asking the owner

Question is the one form for asking a person anything [R9]: the documentation fixer's (a possible code defect; any edit that would change mathematics), Bug hunt's, Change audit's concerns, the code fixer's approvals and the attempts that hit its cap, the keep-or-revert a run's close puts when code changed outside the guarded commit (§10), rule counterexamples, and proposed program checks. The wiring check regenerates, or exits 2 when it cannot read the config, and the session then asks through a Question kept outside a run.

How the language rules are applied. Questions.check(q, cfg) runs whenever a question is put, inside a run or out of one, never when a record is read [an older record would fail to load under a newer rule]. It selects, at that moment, every program rule in RULES whose input is a question, so no rule text is copied and a changed rule applies to the next question. These check, for example: a decision of one sentence ending in a question mark; a length limit; no rule id, finding id, file path or code name in the decision or context (those go in items and exhibit); no word on the rule's list of the tooling package's own terms (a Parameter). The agent-checked language rules — plain, self-contained, no invented jargon — are judged by one agent before questions are shown. A failing question is rewritten once, then shown with the failed rule named; report.md ends with the rendered questions, and test/questions.jl checks every question form built.

Answers. gbg answer <question> [item] <option> [direction] records the answer, and any direction with it, on the question or the named item: in the run record for a run's questions, otherwise in .gbg/questions.json. Each question's CodeFix (§4.4) is written beside it in the same place. An answered question never returns: grading and later runs skip any finding whose question has an answer, unless the answer was "fix the documentation instead" — that finding waits for the next run of its instrument, where the documentation fixer takes it. An owner's "not a defect, do not ask again" appends a Settled value to .gbg/settled.jl, tied to the question id and holding the anchored locations it covers. ConfigIO parses that file and Agents is its only reader, telling agents "do not report" while each of those locations still re-anchors (§4.5); no build, test or check reads it [settled choices were raised again in 4 of 87 findings].

9. Applicability

A package turns a rule, an agent role or a whole instrument off with a Switch naming it and giving the reason, and sets a variant with a Setting [R10]. Every element that is off is listed in the config and shown, with its reason, on the package's documentation site; an unknown target or a missing reason is exit 2.

A third state, the deferral [Phase 5]. A switch says a rule does not apply and is an answer; a Deferral says the package means to meet a rule and has not yet, and is a question with a condition on it — until, what would close it. Recording "not yet" as a switch buries an intention in a file nobody revisits and publishes "does not apply" where the truth is "owed". A deferred rule reports nothing in a build or a test — a deferral never fails a build — and is listed beside the switches on the package's site and printed by gbg check. A rule cannot be both switched off and deferred.

Every rule is switchable. There is no set a package may not escape [as ruled 2026-09-17]. The rulebook is the DEFAULT, and a package overrides any part of it by saying so where a reader can see it. An earlier draft marked some rules — the ones catching text that renders wrongly, and the docstring-structure rules — as always on, and that mark was never set, because the two things it would have bought are already bought by the switch itself. A switch cannot be silent: it names the rule, gives the reason, and is rendered into the package's own rulebook and onto the one small tooling page of its site, so the escape is on the record either way. What the mark added was only the refusal — and its cost is a package with a red build and no way out but a MAJOR release of this one, which makes this package the obstacle rather than the help.

Off in GBGCodingTools, with reasons:

  • the LaTeX notation and spacing rules and the citation rules — its documentation contains no mathematics and cites no literature;
  • running Literate examples — it ships none;
  • the documentation review itself, until Phase 8 turns self-application on; what Bug hunt and Change audit derive as readers (Phase 6) is switched off here when they exist.

Settings here: a docstring's first sentence says what the operation does (science packages: the physical meaning of what it computes); the "written by AI" banner is on every page.

10. How a run starts, works and stops

Start. A run starts only on the owner's request, in words or by slash command (as ruled), with one exception: the single Change audit of an approved code fix (§4.4), which the owner's "fix the code" authorises with the fix and which starts nothing further. Nothing else — no gate, no check, no other fix, no other run — starts a run [in the past, 8 of 15 rounds here were opened by the session or by a gate]. Once started, a run fixes and verifies to its end without asking again. A run interrupted before its end — an outage, the plan's tokens gone, a session that ended — is continued by the next session on its own, which says so in the chat and waits only if the tree moved since; nothing of an unfinished stage is taken. gbg run abandon ends one the owner does not want continued, as OWNER_STOPPED, its findings dropped [ruled 2026-09-21]. gbg run <instrument> --readers bound|open|both says which readers (§5.2), bound by default; --scope full|changed (Phase 4d) whether the whole corpus is read or what changed since the last finished run of that combination, a tool bump or a config or switch change since making the next run full [ruled 2026-09-21]; the "tool bump" is read as the rules moving, by a digest of the rulebook the run records, and a change to the docs build's script counts as a config change, since it decides what every page is built from. gbg run start exits 2 when the working tree is not clean, another run is open, or the instrument has no readers, and records the version of GBGCodingTools, the digest of its rulebook, the first commit, the readers and the pass budget.

Carried findings, and the two places they live. Open findings carry over, as ruled. The run record keeps them with their ids and anchored locations: the machine's copy, which the next run of that instrument starts from, before its own search. That next run re-anchors each one first (§4.5); what comes back OUTDATED — the text it was about is gone or rewritten past recognition — is closed as no longer locatable and said so in the report, not carried for ever. At close, every instrument but the leak scan also writes one line per leftover into .claude/WORK_QUEUE.md, the owner's list — a review's unfixed findings, a hunt's confirmed defects whose question is unanswered, an audit's concerns — each naming the file, the node and the quote rather than a line number, stale by the time the owner reads it. Those lines go under a heading the end-of-turn guard does not count, so the list never makes a session work on something the owner has not asked about [a session held to that list could only edit by hand or open a run nobody asked for]. The report keeps no second list of leftovers: it names the run record and says how many lines went to the queue.

Work. Runs orders the stages; the session launches each one (§6). Documentation review: start → find → collect → fix → verify → collect (one pass, §4.3) → close. Bug hunt: start → hunt, one hunter per code area of the config and the open readers → collect → agents write failing tests → gbg run witnesses runs them → collect → close. Change audit: start → audit → collect → close, the package's named tests run as evidence. gbg run close writes run.json and report.md — for a leak scan, neither (§3). The session commits and pushes what was written, shows the report and questions, and ends.

End, decided by a program and recorded in Run.stop, whatever the §3 table's ordinary ending says: DONE (nothing open, or the fourth pass made and what is open carried over [ruled 2026-09-21: the pass cap is about convergence, not a budget]); CANNOT_EVALUATE (a step exited 2 or 3; the instrument is not repaired inside the run, which rounds that patched their own scripts showed the need of); OWNER_STOPPED. Close also runs two programs:

  • it classifies every commit since the run's first commit; if any changed code outside gbg docfix commit, the run ends CANNOT_EVALUATE and the owner is asked to keep or revert it, with an exhibit the program writes;
  • it runs gbg docfix check; if the build is red, it restores the documentation to the last commit that passed and commits that through gbg docfix commit [a red docs build would otherwise stay on the branch].

A run never searches twice, makes a fifth pass, commits code outside test/regressions/escalated/ (§4.4 step 3), starts another run, or changes an instrument (instruments are code); discarded bug-hunt candidates are listed with their passing tests [one was a real blocker].

Across runs. No build, test or wiring check reads a run record, the question store or the settled rulings [review state turned science tests red]. The work-queue file and the end-of-turn guard that holds a session to it stay as ruled; a run's close is the only verb writing to that file, one line per leftover, under the uncounted heading.

Release of GBGCodingTools needs a clean tree on master, pushed; a green Pkg.test(), a green docs build and a green wiring check; and the CHANGELOG.md entry; the tag is never moved. gbg release --counts prints, for v2.0.0 alone, what still holds that release (IMPLEMENTATION §6). gbg release prints, and the tag message and that entry carry, two lines it does not act on: the commits whose keep-or-revert question is still open, and how many confirmed failing tests wait unanswered in test/regressions/escalated/. Nothing else holds a release: no review run, no open finding, no unanswered question, no audit.

Who stops. Inside a run, the program, from the pass cap; there is no ceiling on launches — the panel over the units, one relaunch each, one verifier per place holding open findings and one pass bound a run by design [ruled 2026-09-21; one pass and one verifier, 2026-09-26]. Across runs, the owner, by asking or not. A program-decided loop needs no budget: it ends itself by passing (§4); the code fixer's three attempts are a judgement about the fixer, not a budget (§4.4 step 2).

11. How GBGCodingTools plugs into a package

The pinned version. Config.tool names one released version (as ruled) — :dev only in the tooling package's own checkout — which gbg sync writes into each environment naming the tool, and into neither package's own dependencies. gbg bump runs only on the owner's request; it changes the pin and regenerates every generated part, checking nothing first: the new rules arrive only when the environments move, so the next build under them judges the package.

Inside a science package's Pkg.test() the code rules run and the wiring check compares, and inside its docs build the documentation rules run and the wiring check compares again; regenerating anything is left to gbg sync, gbg bump and gbg release, so a build only reports what has drifted. GBGCodingTools' own test suite runs more, being the tooling package's: test/rules.jl (which materialises every example), test/guard.jl, test/anchors.jl, test/questions.jl and test/architecture.jl.

GBGCodingTools.Engine.Harness.test(root; extra = MY_RULES)    # test/runtests.jl: the rulebook, then the package's own
GBGCodingTools.makedocs(GBGCodingTools.ConfigIO.read_config(path); sitename = "MyPackage", pages = [...])

The package's own preparation (Literate output, copied rationale pages) runs in docs/make.jl before makedocs; its outputs are declared copies or generated paths. The wrapper makedocs runs the documentation rules over the source, then Documenter.makedocs, then the rules over the built site, and throws on any finding. Both entry points are deterministic and offline, agree on a fresh clone and on CI, and never read run records, questions, settled rulings or git state. A used file set matching no file is exit 2, and literal docstrings in the source must match the loaded module's [a check with no input reports clean].

The same files in every package, including GBGCodingTools, created by gbg init:

.gbg/settled.jl              the owner's settled rulings, appended on "do not ask again"
.gbg/questions.json          questions put outside a run, with their answers
.gbg/policy/*.md             generated
.gbg/runs/<id>/              run.json and report.md; while a run is open, its stage file and draft record

.claude/settings.json        the end-of-turn hook, generated

Agent output lives under .gbg/scratch/, which git ignores; the driver is this package's own tracked file (§5.1).

gbg init never overwrites what the package wrote itself. Four of those paths are commonly a package's own before the tooling arrives — a CI workflow, .claude/settings.json, the work queue, and a skill whose name is already taken by one of the package's commands. Where a file exists and did not come from a generator, init writes everything else, prints the difference for each collision and exits 1; the owner moves or keeps his own file and runs it again [a generated file silently replacing a hand-written workflow is the one wiring mistake that is noticed late]. Unwiring a package is reverting the commits that wired it, after which gbg finds no config there and refuses.

12. What is shown to work, and what is not

Program checks are shown to work by their examples (§5.2): every check is run on every example of its rule, and its locations must equal what the example expects, in both directions and for every clause. Re-anchoring is shown the same way, by test/anchors.jl, which uses Runs.reanchor and so is one of the tooling package's own tests (§5.1): a .jl and a Markdown fixture found again after lines are inserted above them, after a binding is renamed, after the quote is reworded, and after both are gone (OUTDATED, never a guess).

The instruments whose findings come from agents are not measured: nothing plants known defects to count how many are found. This is a deliberate limit, not a plan: a change to an agent role's wording, rule list or strength cannot be shown to help or hurt, and whether they are worth their cost stays the owner's judgement, from what their reports contain. Every number in brackets is past evidence — from the science packages' review rounds and this package's own — kept as the reason a mechanism exists; nothing re-measures them from now on, so a role once justified by such a number stays justified only by it. Each run records what is factual and cheap: findings reported, fixes verified, items carried over, agent launches used and, where the platform reports it, tokens.

One thing about the rulebook is measured: whether a rule's text says one thing. Three blind readers, given only the rules' text, tag what deciding each needs; their agreement (Fleiss' kappa) and the rules they flag as underspecified are reported, and the majority becomes the tag. Round 0 → 1 on 2026-09-19: material 0.74 → 0.90, flags 18 → 8, splits 9 The rule wording study (Phase 4e) is that procedure as a verb; it proposes, and a tag changes only on an answer.

13. Change control and growth

A rule, agent role, discipline or instrument is code in GBGCodingTools, apart from the prose fields of §4.2: it changes through the code fixer on the owner's answer to a finding, or by the session on the owner's direct answer, is released as a tag that is never moved, and reaches a package through gbg bump [R2]; it never changes during a run. A design review is FUTURE WORK, not an instrument, and has no row in §3: gbg attack would run agents over this design and produce proposals, never findings, each becoming a question to the owner or dismissed with its reason. It would write no tracked file — no run record, no report, no work-queue line — so it has no row in §6 either: its proposals reach the owner as questions in the session that ran it, the way a leak scan's findings do [as ruled]. Deferred on 2026-09-21 so that this package reaches its consumers sooner; nothing depends on it, and nothing it would check is unchecked meanwhile, because the rulebook's TEXT is the subject of the rule wording study (§12) and not of an attack. Two things are asked of it whenever it is built. It attacks a MECHANISM — a reader panel, a guard, a lens set — and never prose, and it demands of every attacker a concrete EVADING EXAMPLE: the defect that passes, where it sits, and why each part of the mechanism misses it. An attack that only collects objections converges by narrowing what the thing under attack claims, which is a measured failure of this project and not a hypothetical one [the six discipline texts, seven rounds to no objection, 2026-09-21].

Retiring a rule. A rule leaves the rulebook by having its value removed, which is a code change like any other: the owner's answer names the id and why the rule is no longer worth keeping, Catalogue.RETIRED and the CHANGELOG entry record the removal, the id is never reused [an id reused for a different rule makes every older record lie], and a switch naming it stays legal. This is the counterpart of unchecked_reason, which says why a rule no program can check is kept: retirement is how one that should not be kept is dropped on the record rather than quietly [as ruled].

Growth limit. A code change adding a mechanism — a rule, a bundle or standpoint of readers, a discipline, an instrument, run stage, verb or refusal — names, in its question, the requirement or failure it answers and what it replaces; without one it is not added.
